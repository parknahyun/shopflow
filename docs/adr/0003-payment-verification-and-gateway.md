# ADR-0003: 결제 검증과 대행사 연동

- **상태**: 승인됨 (2026-10-12, 사용자 승인, ADR-0009 수정 반영)
- **날짜**: 2026-10-08
- **관련 이슈**: #3

## 맥락

헌법은 카드번호 원문을 저장하지 않고, 결제 결과를 서버에서 검증하고, 청구 금액을 서버의 주문 총액과 대조하라고 정했다(원칙 II). 즉시 결제와 가상계좌(입금 대기)를 모두 지원해야 하고(FR-008a), 입금 완료는 웹훅으로 받는다.

## 결정

1. **서버 직접 검증**: 고객은 대행사 결제창에서 결제한다. 돌아온 결과를 믿지 않고, 서버가 대행사에 결과를 직접 조회해 상태, 주문 번호, 금액을 주문 총액과 대조한 뒤 확정한다. 웹훅도 같은 조회로 다시 확인한다.
2. **포트로 격리**: 결제를 `PaymentGateway` 포트(준비, 승인, 조회, 환불)로 감싸고 도메인 코드는 포트만 쓴다. 테스트에서는 가짜 구현을 쓴다.
3. **대행사**: 토스페이먼츠를 쓴다. 카드와 가상계좌, 웹훅, 멱등키 헤더를 지원하고 개발용 테스트 키가 있다.
4. 대행사 호출이 시간 초과로 끝나 결과를 알 수 없으면 조회로 확인하기 전까지 재고를 반환하지 않는다.

## 수정 (2026-10-12, 설계 검토 반영, [ADR-0009](0009-review-decisions-payment-refund-scope.md))

- 결제 시작 요청은 **고객이 확인한 금액**을 함께 보내고, 서버가 계산한 주문 총액과 다르면 결제를 시작하지 않는다.
- 대행사에서 돌아온 결과는 **읽기 전용 반환 경로**로 보여 주기만 하고, 확정은 멱등키가 있는 **POST 승인 확인**으로만 한다. 확정과 재고 반환은 서버가 대행사에 직접 조회한 결과로만 한다.
- 결제를 만료시키기 전에 항상 대행사에 **조회를 먼저** 한다. 만료나 취소 뒤에 승인이나 입금이 확인되면 주문을 "확인 필요"로 기록하고 **자동으로 전액 환불**한다(주문은 환불됨으로 끝난다).
- **환불은 별도 개체**다. 취소와 같은 트랜잭션에서 "요청" 행을 먼저 기록한 뒤 대행사를 호출한다. 실패하거나 결과를 알 수 없으면 재시도·재조회 작업이 이어 간다. 하위 주문 하나에 진행 중이거나 완료된 환불은 하나뿐이고, 환불 합계는 금액을 넘을 수 없다(데이터베이스 제약으로 막는다).
- **가상계좌 결제의 환불에는 환불 계좌**(은행, 계좌번호, 예금주)가 필요하다. 입금 대기로 결제를 시작할 때 받고, 계좌번호는 암호화해서 저장하고 로그에 남기지 않으며 환불 후 마스킹한다. 대행사별 환불 계좌 요구 사양은 구현 전에 확인한다.
- 비동기 결제 결과(웹훅, 승인 확인, 만료 작업)는 `PaymentResultCoordinator`가 지휘한다.
- 이 ADR의 "토스페이먼츠 선택"은 개발용 테스트 키 범위에서 확정한다. 운영 계약과 키 발급은 이번 범위 밖이다.
## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|------|--------------------|
| 포트원(여러 대행사 중개) | 대행사 교체는 쉽지만 한 단계가 더 늘어 첫 기능에는 과하다. |
| 대행사와 직접 계약 | 심사 기간이 길어 첫 기능에 맞지 않는다. |
| 결제창 반환값을 그대로 신뢰 | 금액 위조와 중복 승인 위험이 있어 헌법 원칙 II에 어긋난다. |

## 결과

- **좋은 점**: 카드번호가 서버를 지나가지 않는다. 대행사를 바꿔도 도메인 코드는 그대로다. 대행사 없이 실패, 시간 초과, 웹훅 중복 시나리오를 테스트할 수 있다.
- **감수할 점**: 승인 때마다 조회 호출이 한 번 더 필요하다. 실제 가맹 계약과 운영 키 발급은 이번 범위 밖이며, 확정 전에 대행사 선택을 사람이 검토해야 한다.
