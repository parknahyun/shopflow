# ADR-0006: 기본 기술 스택과 구조

- **상태**: 승인됨 (스프링 부트와 템플릿 엔진은 직접 지정했고, 타임리프와 모듈형 모놀리스 구조는 제안을 받아들인 것이다)
- **날짜**: 2026-10-08
- **관련 이슈**: #3

## 맥락

헌법은 스프링과 서버 사이드 템플릿 엔진으로 만들라고 정했다(기술 스택 섹션). 템플릿 엔진 종류와 코드 구조는 정해지지 않았다. 첫 기능부터 결제, 재고, 정산 같은 정합성이 중요한 기능을 다루므로 구조가 단순해야 테스트와 검증이 쉽다(원칙 IV).

## 결정

- 스프링 부트 3.x(자바 21)로 만든 **서버 렌더링 웹 애플리케이션**이다.
- 화면은 **타임리프**를 쓴다. 스프링 MVC와 기본으로 연동된다.
- 인증과 인가는 스프링 시큐리티, 데이터 접근은 스프링 데이터 JPA를 쓴다.
- 구조는 **단일 프로젝트의 모듈형 모놀리스**다. 기능 단위 패키지(계정, 상품, 장바구니, 재고, 주문, 결제, 배송)로 나누고, 패키지 사이 호출은 서비스 인터페이스로만 한다.
- 빌드 도구는 그레이들, 데이터베이스는 포스트그레스큐엘과 플라이웨이를 쓴다. 테스트는 같은 데이터베이스를 테스트컨테이너스로 띄운다.
- 별도의 단일 페이지 앱 프론트엔드나 메시지 큐, 캐시는 이번 범위에 도입하지 않는다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|------|--------------------|
| 마이크로서비스 | 결제와 재고를 한 트랜잭션으로 처리해야 해서 분산 트랜잭션 부담이 크고, 현재 규모에 과하다. |
| SPA 프론트엔드 분리 | 헌법이 서버 사이드 템플릿을 정했고 사이트 간 요청 위조 방어와 화면 구성이 단순해진다. |
| 다른 템플릿 엔진(머스태치, 프리마커) | 스프링 기본 연동과 자료가 가장 풍부한 타임리프를 택했다. 직접 지정이 없어 기본값으로 정했다. |
| 메이븐 | 기능 차이가 크지 않고 스프링 부트 안내가 그레이들 기준이다. |
| 인메모리 데이터베이스(H2)로 테스트 | 잠금과 동시성 동작이 달라 재고 검증을 믿기 어렵다. |

## 결과

- **좋은 점**: 하나의 배포 단위와 하나의 데이터베이스 트랜잭션으로 재고, 주문, 결제 정합성을 지키기 쉽다. 패키지 경계를 지켜 두면 나중에 분리할 수 있다.
- **감수할 점**: 규모가 커지면 단일 애플리케이션이 병목이 될 수 있다. 패키지 경계는 규칙으로 지켜야 하며 자동으로 강제되지 않는다(필요하면 구조 검사 테스트를 추가한다).
