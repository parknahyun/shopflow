# ADR-0002: 멱등키 설계

- **상태**: 승인됨 (2026-10-12, 사용자 승인, ADR-0009 수정 반영)
- **날짜**: 2026-10-08
- **관련 이슈**: #3

## 맥락

중복 클릭, 네트워크 재시도, 결제사 콜백 재전송이 겹쳐도 결제와 환불은 한 번만 일어나야 한다(헌법 원칙 VIII, FR-009, FR-013b). 같은 요청이 동시에 두 번 들어오는 경우도 막아야 한다. 이 규칙은 결제 시작, 결제 승인, 취소·환불, 웹훅 모두에 적용된다.

## 결정

멱등키 전용 테이블을 둔다. (범위, 키)에 유일 제약을 걸고 요청 내용 해시, 처리 상태(처리 중, 완료), 저장된 결과, 만료 시각을 기록한다.

- 같은 키에 같은 내용이 다시 오면 저장된 결과를 그대로 돌려준다.
- 같은 키에 다른 내용이 오면 거절한다(422).
- 처리 중에 같은 키가 들어오면 유일 제약 때문에 한 건만 진행하고 나머지는 "처리 중"을 알린다.
- 적용 범위: 결제 시작, 결제 승인, 취소·환불, 웹훅(대행사 이벤트 식별자를 키로 사용).
- 대행사 API에도 멱등키 헤더를 함께 보낸다.

## 수정 (2026-10-12, 설계 검토 반영, [ADR-0009](0009-review-decisions-payment-refund-scope.md))

- **점유 만료 시각**을 둔다. 처리 중인 키를 서버가 죽어서 놓친 경우, 점유 시간이 지나면 다른 요청이 대행사 조회로 상태를 확인해 이어받거나 실패로 바꾼다. "처리 중"에 영구히 고착되지 않는다.
- 키는 **시도마다 새로 만든다.** 실패한 결과도 저장하며, 재시도는 새 키를 쓴다(같은 키로 재시도하면 저장된 실패 결과가 돌아온다).
- 웹훅은 처리가 **완료된 뒤에만 200**으로 응답한다. 처리 중 오류가 나면 5xx로 응답해 대행사가 다시 보내게 하고, 키를 처리 중으로 남겨 두지 않는다.
- 키의 만료(TTL)와 점유 시간은 설정값으로 두고 기본값을 문서에 적는다.
## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|------|--------------------|
| 애플리케이션 메모리의 중복 방지 | 서버가 여러 대이거나 재시작되면 보호가 사라진다. |
| 주문 상태만 보고 중복 판단 | 동시에 들어온 요청 사이의 경쟁을 막지 못한다. |
| 대행사의 멱등 기능에만 의존 | 우리 쪽 상태 변경(재고, 주문)은 보호되지 않는다. |

## 결과

- **좋은 점**: 동시 요청에도 안전하고 재시작해도 유지된다. 모든 외부 진입점에 같은 규칙을 적용할 수 있다. 자동 테스트로 "같은 키 10번에 결제 1번"을 검증할 수 있다(SC-003).
- **감수할 점**: 요청마다 한 번의 쓰기가 더 필요하다. 오래된 키를 정리하는 작업이 필요하다.
