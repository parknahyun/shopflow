# ADR-0008: 화면 MVC 계층과 스프링 데이터 REST 기반 계층 구조

- **상태**: 제안됨 (스프링 데이터 REST 사용과 화면 MVC 계층 분리는 직접 요청했고, 사용 규칙과 계층 세부는 제안이다)
- **날짜**: 2026-10-08
- **관련 이슈**: #3, #4
- **보완하는 ADR**: [ADR-0006](0006-technology-stack-and-structure.md)(기술 스택과 구조), [ADR-0007](0007-context-deployment-strategy.md)(컨텍스트별 배포 목표)

## 맥락

전통적인 MVC 하나로 화면과 업무를 모두 처리하는 구조 대신, 리포지토리를 REST로 노출하는 방식을 쓰고 프론트엔드를 제어하는 MVC 계층을 따로 두기로 했다. 이유와 제약은 다음과 같다.

- ADR-0007의 목표는 프론트엔드를 나중에 별도 인스턴스로 분리하는 것이다. 화면 계층이 REST API만 부르면 분리할 때 호출 방식만 바뀐다.
- 업무 규칙(재고 조건부 갱신, 하위 주문 상태 전이, 멱등, 판매자별 접근 제한)은 REST로 개체를 그대로 노출하면 쉽게 우회된다. 스프링 데이터 REST는 리포지토리를 자동으로 REST로 노출하므로 이 위험이 크다.
- 헌법은 서버 렌더링 화면(타임리프)과 스프링 시큐리티를 정했다. 헌법 원칙 II는 모든 상태 변경 요청에 사이트 간 요청 위조 방어와 권한 검사를 요구한다.

## 결정

네 층으로 나눈다([컴포넌트 다이어그램](../../specs/001-multiseller-commerce-core/diagrams/c4-component.png)).

1. **화면 MVC 계층(프론트엔드 제어)**: 스프링 MVC 화면 컨트롤러와 타임리프 화면 모델. 화면 흐름, 폼 처리, 오류 문구 변환만 한다. 서비스나 리포지토리를 직접 부르지 않고 **API 클라이언트**(자바 인터페이스)만 쓴다. 첫 구현의 API 클라이언트는 같은 프로세스의 REST API 계층을 직접 호출하고, 프론트엔드를 분리할 때 HTTP 호출 구현으로 바꾼다.
2. **REST API 계층**: 컨텍스트마다 스프링 데이터 REST로 **읽기용 리소스**를 노출하고, 상태를 바꾸는 일은 **동작 컨트롤러**가 맡는다. 재고와 배송 컨텍스트는 REST로 노출하지 않고 서비스 인터페이스로만 쓴다.
3. **서비스 계층**: 업무 규칙, 상태 전이, 조건부 갱신, 멱등 처리, 컨텍스트 사이 조정(결제 시작 조정).
4. **리포지토리 계층**: 스프링 데이터 JPA. 상태 변경은 조건부 갱신 질의로만 한다.

**스프링 데이터 REST 사용 규칙**

- 상태를 가진 개체(재고, 결제, 하위 주문의 상태, 멱등키, 변경 이력)는 쓰기용 REST 리소스로 노출하지 않는다. 필요한 리포지토리는 노출 대상에서 뺀다.
- 상태 전이, 결제 시작, 취소, 구매 확정, 발송 처리, 승인과 거절은 동작 컨트롤러만 하고 반드시 서비스를 거친다. 리소스에 대한 일반 `PUT`, `PATCH`, `DELETE`로는 상태를 바꿀 수 없다.
- 읽기 리소스는 리포지토리의 권한 조건과 메서드 보안으로 본인 것만(판매자는 확정된 주문의 하위 주문만) 돌려준다. 다른 사람 것은 "찾을 수 없음"으로 응답한다.
- 컨텍스트 사이 참조는 식별자 값이라 REST 링크로 이어지지 않는다. 필요한 연결은 화면 계층이 API 클라이언트로 각각 불러 합친다.
- 응답은 공개용 식별자와 필요한 필드만 담는 조회 전용 모양(프로젝션)으로 만든다. 내부 식별자와 비밀번호 해시 같은 필드는 노출하지 않는다.
- REST API 계약(경로, 응답 모양, 오류)은 구현 전에 계약 문서로 정리하고 계약 테스트로 지킨다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|------|--------------------|
| 전통적인 MVC 하나(컨트롤러가 서비스를 직접 호출) | 프론트엔드를 분리할 때 화면과 업무가 섞여 있어 나누기 어렵다. |
| 직접 만든 REST 컨트롤러만 사용(스프링 데이터 REST 없이) | 규칙을 더 확실히 지킬 수 있지만 읽기용 조회와 검색 리소스를 모두 직접 만들어야 한다. 다만 규칙 위반 위험이 큰 영역에서는 이 방식이 더 안전하므로, 문제가 생기면 해당 리소스만 이 방식으로 바꾼다. |
| 스프링 데이터 REST로 쓰기까지 전면 노출 | 상태 전이, 재고 조건부 갱신, 판매자별 접근 제한 같은 규칙을 우회할 수 있어 헌법 원칙 II, III에 어긋난다. |

## 결과

- **좋은 점**: 읽기용 리소스를 적은 코드로 만들 수 있다. 화면 계층이 REST API만 알아서 프론트엔드 분리가 쉽다. 업무 규칙이 서비스 계층 한 곳에 있다.
- **감수할 점**: 스프링 데이터 REST는 노출 범위를 실수로 넓히기 쉽다. 노출 대상과 권한 조건을 점검하는 통합 테스트(쓰기 요청이 거절되는지, 남의 것이 보이지 않는지)가 필요하다. 첫 구현의 API 클라이언트가 같은 프로세스를 직접 부르는 구조라, HTTP로 바꿀 때 오류와 시간 초과 처리를 새로 설계해야 한다. 응답 모양(링크 형식)이 화면 모델에 영향을 주므로 화면 모델 변환 계층이 필요하다.
- **후속 작업**: REST API 계약 문서를 `specs/001-multiseller-commerce-core/contracts/`에 쓴다. 기존 `web-routes.md`는 화면 MVC 계층의 화면 경로로 위치를 다시 정리한다. 작업 목록에 "쓰기 거절과 권한 조건 통합 테스트", "REST 노출 범위 점검"을 넣는다.
