# ADR-0009: 설계 검토에 따른 결제·환불 체계와 범위 결정

- **상태**: 승인됨 (2026-10-12, 사용자가 "추천대로 확정"을 선택했다)
- **날짜**: 2026-10-12
- **관련 이슈**: #3
- **보완하는 ADR**: [ADR-0001](0001-inventory-reservation.md), [ADR-0002](0002-idempotency-key.md), [ADR-0003](0003-payment-verification-and-gateway.md), [ADR-0008](0008-layered-rest-repository.md)

## 맥락

설계자, 개발자, 고객, 판매자 네 관점으로 설계를 비판적으로 검토했다([review.md](../../specs/001-multiseller-commerce-core/review.md)). 돈과 재고가 깨지는 문제(R-01~R-11)와 사용자가 막다른 길에 놓이는 문제(P-01~P-09), 문서 간 모순이 확인됐다. 이 ADR은 그 결정을 한 곳에 모은다. 명세, 데이터 모델, 유즈케이스, 계약, 작업 목록은 이 문서를 따른다.

## 결정 A. 범위 결정 6건

| # | 결정 | 내용 |
|---|------|------|
| A1 | 확인 필요 주문은 자동 전액 환불한다 | 결제 만료·입금 기한 뒤에 승인이나 입금이 확인되어 "확인 필요"가 된 주문은 결제 금액을 자동으로 전액 환불한다. 환불이 끝나면 주문은 "환불됨"이 된다. 운영자는 조회하고, 자동 환불이 계속 실패하면 사유를 확인한다. |
| A2 | 판매자도 발송 전에 하위 주문을 취소할 수 있다 | 판매자는 자기 하위 주문이 "발송 전"일 때 사유(필수)를 적어 취소할 수 있다. 환불과 재고 가산은 고객 취소와 같은 흐름이다(하위 주문 금액 전액). 발송 기한 초과 자동 취소는 이번 범위에서 빼고, 발송 지연 표시만 한다. |
| A3 | 입점 거절은 사유를 남기고 재신청할 수 있다 | 운영자는 거절할 때 사유를 반드시 적는다. 거절된 판매자는 같은 계정으로 정보와 서류를 고쳐 다시 신청할 수 있다(거절 → 신청). 사업자등록번호 유일 제약은 그대로다(같은 판매자 정보 행을 고쳐서 쓰므로 새 번호 충돌이 없다). |
| A4 | 배송 완료 뒤 고객이 "문제 신고"를 할 수 있다 | 배송 완료된 하위 주문에서 구매 확정 전에 고객이 문제를 신고하면 자동 구매 확정에서 빠지고 운영자가 조회한다. 신고 처리(환불, 반품, 분쟁 중재)는 다음 기능에서 다룬다. 이번 범위는 표시와 조회뿐이다. |
| A5 | 정지는 신규 판매만 막는다 | 정지된 판매자의 상품은 고객에게 보이지 않고 새 상품을 등록할 수 없다. 이미 결제된 진행 중 주문의 발송 처리, 배송 완료 처리, 판매자 취소는 계속할 수 있다. |
| A6 | 결제 대기 주문을 고객이 취소할 수 있다 | 결제 대기 주문은 고객이 주문 단위로 취소할 수 있다(재고 반환, 결제 만료, 하위 주문 취소). 결제수단 변경은 취소 후 다시 주문하는 것으로 대신한다. |

## 결정 B. 상태와 데이터 모델 변경

### B1. 주문 상태

상태: 결제 대기, 확정, 취소됨, 확인 필요, **환불됨**(새로 추가).

| 현재 상태 | 이동 가능한 상태 | 조건 |
|-----------|------------------|------|
| 결제 대기 | 확정 | 결제 성공 확인 |
| 결제 대기 | 취소됨 | 결제 실패, 시간 초과, 입금 기한 만료, **고객 직접 취소(A6)** |
| 결제 대기 | 확인 필요 | 재고 확보 만료 뒤 결제 성공 |
| 취소됨 | 확인 필요 | **만료로 취소된 뒤 승인이나 입금이 확인됨(만료 뒤 성공)** |
| 확정 | 취소됨 | 모든 하위 주문이 취소됨 |
| 확인 필요 | 환불됨 | 자동 전액 환불 완료(A1) |
| 환불됨, 취소됨(확정 이후) | (없음) | 종료 |

- 주문에 **확인 필요 사유**(기한 후 입금, 재고 확보 만료 뒤 결제 성공, 금액 불일치)를 기록한다.
- 총 금액은 "주문 생성 시점의 하위 주문 금액 합계"이며, 이후 일부 취소로 바뀌지 않는다. 남은 금액은 취소되지 않은 하위 주문 금액으로 계산한다.

### B2. 하위 주문

- 취소는 **속한 주문이 확정된 뒤에만** 할 수 있다(결제 대기 주문의 하위 주문 단독 취소는 거절한다. 결제 대기 주문은 A6의 주문 단위 취소만 있다). 재고 이중 반환을 막는다.
- **취소 주체**(고객, 판매자, 시스템)와 **취소 사유**(판매자 취소는 필수)를 기록한다.
- **문제 신고 시각**과 **문제 신고 사유**를 가진다(A4). 신고된 하위 주문은 자동 구매 확정 대상에서 빠진다.
- 상태 전이는 기존 허용 목록 그대로다(발송 전 → 배송 중/취소, 배송 중 → 배송 완료, 배송 완료 → 구매 확정).
- 자동 구매 확정은 `배송 완료 시각` 기준이다(배송 컨텍스트의 값을 하위 주문이 복사해 가지거나 서비스 인터페이스로 조회한다. `updated_at`을 기준으로 쓰지 않는다).

### B3. 결제 상태와 환불

결제 상태: 준비, 승인 대기, 입금 대기, 성공, 실패, 만료. 전이 변경:

- **준비 → 만료**를 추가한다(결제창에 들어가지 않고 이탈한 경우).
- **만료 → 성공**을 추가한다(조건: 만료 뒤 승인이나 입금이 서버 조회로 확인됨. 주문은 확인 필요로 간다. 이 경우만 만료가 종료 상태가 아니다).
- 입금 대기 결제의 만료는 입금 기한 기준이며 **UC-18이 담당**한다. 재고 확보 만료 처리(UC-17)는 입금 대기 결제를 만료시키지 않는다.
- 주문당 **비종료 결제는 하나만** 있다(준비, 승인 대기, 입금 대기 중 하나). 데이터베이스 부분 유일 인덱스로 강제한다.
- 만료 처리 전에 항상 대행사에 **조회를 먼저** 한다.

**환불**을 별도 개체로 둔다.

- 환불: 결제 참조, 대상(하위 주문 또는 주문 전체), 금액, 사유(고객 취소, 판매자 취소, 확인 필요 환불, 결제 대기 취소), 상태(요청, 확인 중, 완료, 실패), 멱등키, 대행사 환불 키(선택), 요청 시각.
- 상태 전이: 요청 → 완료 / 실패 / 확인 중, 확인 중 → 완료 / 실패. 실패는 재시도 작업이 새 요청으로 이어 간다.
- 환불 행은 **취소(상태 변경)와 같은 트랜잭션에서 "요청"으로 먼저 기록**한 뒤 대행사를 호출한다. 서버가 중간에 죽어도 재시도 작업이 요청 행을 찾아 이어 간다.
- 하위 주문 하나에 **완료 또는 진행 중인 환불은 하나만** 있다(부분 유일 인덱스). 하위 주문별 환불 합계는 그 하위 주문 금액을 넘을 수 없다(조건부 삽입과 DB 제약으로 막는다).
- 환불이 완료되면 결제 거래 내역(추가 전용)에 환불 행을 더한다. 결제 상태는 바꾸지 않는다.
- **가상계좌(입금 대기) 결제의 환불에는 환불 계좌**(은행, 계좌번호, 예금주)가 필요하다. 입금 대기 방식으로 결제를 시작할 때 고객이 입력하고, 계좌번호는 암호화해서 저장하며 로그에 남기지 않는다. 환불이 완료되면 마스킹한다. 대행사별 환불 계좌 요구 사양은 구현 전에 확인한다.

### B4. 재고

- 재고 확보 상태는 **확정으로 두는 방식을 확정**한다(취소 전용 상태를 만들지 않는다. T127 결정). 취소 시 재고 가산은 "발송 전 → 취소" 조건부 갱신과 **같은 트랜잭션에서 한 번만** 한다.
- **고객당 동시 결제 대기 주문 수 상한**(기본 3건)과 한 주문의 판매 단위별 수량 상한(기본 10개)을 설정값으로 둔다. 입금 대기 유지 시간(기본 24시간)은 판매 단위별 상한을 설정으로 둘 수 있다.
- 같은 고객이 결제 대기 주문이 있는 상태에서 새 결제를 시작하면, 상한을 넘기 전까지는 허용하고 넘으면 기존 결제 대기 주문을 먼저 취소하라고 안내한다.
- 판매자의 재고 수정은 **"총 보유 수량" 입력**으로 한다. 서버가 선점되어 묶인 수량과 판매된 수량을 뺀 가용 수량을 계산해 반영하고, 버전 검사로 동시 수정을 거절한다. 음수가 되는 입력은 거절한다.

### B5. 판매자

- 거절 사유 필드(필수 입력)를 둔다. 판매자는 자기 입점 상태와 거절 사유를 조회할 수 있다(로그인 가능).
- 상태 전이: 신청 → 승인 또는 거절, 승인 → 정지, 정지 → 승인, **거절 → 신청**(재신청). 입점 서류는 신청·거절 상태에서 다시 올릴 수 있다.
- 정지된 판매자는 진행 중 주문(이미 확정된 주문의 하위 주문)을 계속 처리할 수 있다(A5).

### B6. 멱등키와 웹훅

- 멱등키에 **점유 만료 시각**을 둔다. 처리 중인 키는 점유 시간이 지나면 다른 요청이 대행사 조회로 상태를 확인해 이어받거나 실패로 바꾼다.
- 키는 **시도마다 새로 만든다**. 실패한 결과도 저장하며, 재시도는 새 키를 쓴다.
- 웹훅은 처리가 **완료된 뒤에만 200**을 준다. 처리 중 오류가 나면 5xx로 응답해 대행사가 다시 보내게 하고, 키는 처리 중으로 남기지 않는다(점유 만료로 회수한다).

### B7. 결제 시작과 승인 확인

- 결제 시작 요청은 **고객이 확인한 금액**을 함께 보낸다. 서버가 계산한 주문 총액과 다르면 결제를 시작하지 않고 새 금액으로 다시 확인하게 한다(FR-010).
- 대행사에서 돌아온 결과 처리는 **멱등키가 있는 POST**로만 한다. 화면의 반환 경로(성공, 실패)는 읽기 전용이다. 확정과 재고 반환은 서버가 대행사 조회 결과로만 한다.

## 결정 C. 구조

- **화면 MVC 계층을 이 백엔드에서 뺀다.** 백엔드는 REST API만 낸다. 화면은 9단계의 별도 프론트엔드 인스턴스이고 HTTP로 호출한다. 같은 프로세스 API 클라이언트도 없다([ADR-0008](0008-layered-rest-repository.md) 수정).
- 스프링 데이터 REST는 **단순 읽기 목록**(상품, 본인 주문, 본인 하위 주문)에만 쓴다. 상태 변경은 동작 컨트롤러만 한다.
- 비동기 결제 결과(웹훅, 승인 확인, 만료 작업)를 지휘하는 **`PaymentResultCoordinator`** 를 둔다. 스케줄러는 컨텍스트 저장소를 직접 부르지 않고 이 조정 서비스를 호출한다.

## 결과

- **좋은 점**: 돈이 나갔는데 주문이 없는 경우가 사라진다. 판매자와 고객이 막다른 길에 놓이지 않는다. 재고 이중 반환과 환불 이중 처리를 데이터베이스가 막는다.
- **감수할 점**: 범위가 늘었다(환불 자동화, 판매자 취소, 재신청, 문제 신고 표시, 결제 대기 취소). 환불 계좌는 개인정보라 암호화와 마스킹 규칙이 필요하다. 가상계좌 환불 사양은 대행사 문서로 확인해야 한다.
