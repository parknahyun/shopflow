# ADR-0007: 컨텍스트별 배포 목표와 단계적 전환

- **상태**: 승인됨
- **날짜**: 2026-10-08
- **관련 이슈**: #3, #4
- **보완하는 ADR**: [ADR-0006](0006-technology-stack-and-structure.md)(첫 구현은 모듈형 모놀리스)

## 맥락

바운디드 컨텍스트(계정, 상품, 주문, 재고, 결제, 배송, 공통)별로 별도 인스턴스를 만들고, 나중에는 프론트엔드도 별도 인스턴스로 분리한다는 방향이 제시되었다. 이 방향은 지금까지 정한 결정과 부딪힌다.

- ADR-0006은 단일 프로젝트의 모듈형 모놀리스를 정했다.
- ADR-0001은 재고 차감과 주문 생성을 한 데이터베이스 트랜잭션으로 묶는다. 컨텍스트가 인스턴스로 나뉘면 불가능하다.
- ADR-0002의 멱등키 테이블은 한 데이터베이스를 전제한다.
- 취소와 발송이 동시에 올 때 먼저 처리된 요청만 반영하는 규칙(FR-013b)은 하위 주문 상태 한 곳의 조건부 갱신에 의존한다.
- 헌법 원칙 IV는 복잡성을 더하려면 근거를 계획서에 적으라고 한다. 프론트엔드를 단일 페이지 앱으로 분리하면 기술 스택 섹션의 근거 기록도 필요하다.

지금 규모와 범위에서 인스턴스 7개를 바로 운영하면, 이번 기능의 핵심 성공 기준(결제 한 번, 동시 주문 정확히 1건, 재고 100% 반환)을 검증하기가 가장 어려워진다.

## 결정

1. **목표 구조**는 컨텍스트마다 별도 인스턴스(와 자기 데이터베이스)로 배포하고, 프론트엔드도 나중에 별도 인스턴스로 분리하는 것이다.
2. **첫 구현은 분리 가능한 모듈형 모놀리스**로 한다(ADR-0006 유지). 인스턴스 분리는 아래 규칙을 지킨 채 필요한 시점에 한 컨텍스트씩 진행한다.
3. **분리 가능성을 지키는 규칙**을 첫 구현부터 적용한다.
   - 컨텍스트 사이 참조는 식별자 값으로만 한다. 외래키와 조인을 컨텍스트 사이에 쓰지 않는다.
   - 컨텍스트마다 자기 테이블만 읽고 쓴다. 다른 컨텍스트의 데이터는 서비스 인터페이스로만 얻는다.
   - 컨텍스트를 가로지르는 흐름(결제 시작, 결제 성공, 발송 전 취소)은 한 곳의 조정 서비스가 맡고, 각 단계를 멱등하게 만든다. 첫 구현에서는 한 데이터베이스 트랜잭션으로 묶지만, 분리할 때는 보상 처리가 있는 흐름으로 바꿀 수 있어야 한다.
   - 컨텍스트마다 마이그레이션 폴더와 멱등키 사용 범위를 따로 둔다.
   - 화면(타임리프)은 서비스 인터페이스만 호출한다. 프론트엔드를 분리할 때 호출 대상만 바뀌게 한다.
   - 판매 단위별 재고 수량은 재고 컨텍스트가 소유한다. 상품 컨텍스트는 재고 수량을 갖지 않는다.
4. **분리 순서 제안**: 결제(외부 연동이 있어 격리 이득이 큼), 프론트엔드, 이후 재고와 배송. 계정, 상품, 주문은 마지막까지 함께 두는 것을 기본으로 한다. 구체적인 시점은 실제 필요(독립 배포, 팀 분리, 성능 병목)가 생길 때 새 ADR로 정한다.
5. 분리 시점에는 헌법 원칙 IV에 따라 계획서의 복잡성 추적 표에 정당화를 적는다.

## 검토한 대안

| 대안 | 채택하지 않은 이유 |
|------|--------------------|
| 처음부터 컨텍스트별 별도 인스턴스 | 재고 선점, 결제, 취소의 정합성을 보상 처리와 메시지 전달로 설계해야 하고, 첫 기능의 검증 난이도가 가장 높아진다. ADR-0001, 0002, 0006과 데이터 모델을 모두 다시 써야 한다. |
| 영구적인 모놀리스(분리 계획 없음) | 목표 방향과 맞지 않고, 경계 규칙이 없으면 나중에 분리하기 어려워진다. |

## 결과

- **좋은 점**: 첫 기능에서 정합성을 한 데이터베이스 트랜잭션으로 검증할 수 있다. 경계 규칙 덕분에 나중에 분리해도 데이터 모델과 코드의 큰 수정이 필요 없다. 재고 소유가 명확해졌다.
- **감수할 점**: 규칙(외래키 금지, 자기 테이블만 사용)은 자동으로 강제되지 않아 구조 검사 테스트가 필요하다. 첫 구현이 한 트랜잭션으로 묶는 흐름은 분리할 때 보상 처리로 다시 짜야 한다. 컨텍스트 사이 데이터 무결성은 데이터베이스가 아니라 애플리케이션이 지킨다.
- **분리 시 필요한 변화**: 컨텍스트별 데이터베이스, 보상 처리와 아웃박스, 서비스 간 계약과 버전 관리, 컨텍스트별 멱등키, 취소와 발송 경쟁 처리를 주문 서비스 한 곳에서 맡기는 설계(배송은 주문 서비스에 상태 변경을 요청).
