# 계약: 결제 포트와 웹훅

도메인 코드는 결제 대행사(토스페이먼츠)를 직접 부르지 않고 `PaymentGateway` 포트만 쓴다. 운영 구현은 대행사 API를 호출하고, 테스트 구현은 가짜 응답을 돌려준다. 결과 처리의 순서는 `PaymentResultCoordinator`가 지휘하며 스케줄러는 이 조정 서비스를 통해서만 포트를 쓴다([ADR-0009](../../../docs/adr/0009-review-decisions-payment-refund-scope.md)).

## 포트 동작

| 동작 | 입력 | 출력 | 설명 |
|------|------|------|------|
| `prepare` | 주문 공개식별자, 금액, 결제 방식, 멱등키 | 결제창 접속 정보 또는 가상계좌 정보(은행, 계좌, 입금 기한) | 결제를 준비한다 |
| `confirm` | 대행사 결제 키, 주문 공개식별자, 금액, 멱등키 | 승인 결과(성공, 실패, 금액) | 즉시 결제를 승인한다 |
| `query` | 대행사 결제 키 | 현재 결제 상태(승인 대기, 입금 대기, 성공, 실패, 만료)와 금액 | 결과를 서버가 직접 확인한다 |
| `refund` | 대행사 결제 키, 환불 금액, 사유, 환불 계좌(가상계좌 결제만: 은행, 계좌번호, 예금주), 멱등키 | 환불 결과(완료, 실패, 결과 모름)와 대행사 환불 키 | 환불을 요청한다 |

## 보장해야 할 규칙

- 같은 멱등키로 `confirm`과 `refund`를 여러 번 불러도 대행사에서 한 번만 처리되어야 한다. 대행사 멱등키 헤더를 쓰고, 우리 쪽 멱등키 테이블에도 결과를 기록한다.
- **멱등키는 시도마다 새로 만든다.** 실패한 결과도 우리 쪽 멱등키 테이블에 저장하고, 재시도(특히 환불 재시도)는 새 키를 쓴다. 같은 키로 다시 부르면 저장된 결과(실패 포함)를 돌려준다.
- 처리 중인 키는 점유 만료 시각이 지나면 다른 요청이 `query`로 상태를 확인해 이어받거나 실패로 바꾼다.
- `confirm`의 금액은 서버가 저장한 주문 총액이어야 한다. 화면에서 받은 금액을 쓰지 않는다.
- 어떤 입력도 카드번호 원문을 담지 않는다. 로그에는 대행사 결제 키와 공개식별자만 남긴다. **환불 계좌번호도 로그에 남기지 않는다.**
- 대행사 호출이 시간 초과로 끝나면 결과를 알 수 없는 상태로 보고, `query`로 확인한 뒤 처리한다. 확인되기 전에는 재고를 반환하지 않는다. 환불 호출이 시간 초과이면 환불 상태를 "확인 중"으로 두고 조회로 확인한다.
- **만료 처리 전에는 항상 `query`를 먼저 부른다.** 조회에서 성공이 확인되면 만료시키지 않고 결제 성공으로 처리한다. 입금 대기 결제는 입금 기한 만료 처리가, 승인 대기·준비 결제는 유지 시간 만료 처리가 맡는다.
- 가상계좌 결제의 `refund`에는 환불 계좌가 필수다. 환불 계좌가 없으면 호출하지 않고 환불을 실패로 기록한다. 대행사별 환불 계좌 요구 사양은 구현 전에 확인한다.

## 환불 상태와 재시도

- 환불은 별도 개체이며 상태는 요청, 확인 중, 완료, 실패다([data-model.md](../data-model.md)). 환불 행은 취소와 같은 트랜잭션에서 "요청"으로 먼저 기록한 뒤 `refund`를 부른다.
- `refund`가 완료를 돌려주면 "완료", 실패를 돌려주면 "실패", 결과를 모르면 "확인 중"으로 바꾼다. 확인 중인 환불은 재시도 작업이 `query`(또는 대행사 환불 조회)로 확인해 완료나 실패로 확정한다.
- 실패한 환불은 재시도 작업이 새 환불 행(새 멱등키, 시도 번호 + 1)으로 이어 간다. 하위 주문(또는 주문 전체)당 진행 중이거나 완료된 환불은 하나이므로 이미 있으면 만들지 않는다.
- 서버가 환불 행만 기록하고 죽었으면 재시도 작업이 "요청"에 멈춘 행을 찾아 호출을 이어 간다.
- 환불이 계속 실패하면 운영자가 실패 사유를 조회한다.

## 웹훅 (입금 대기 방식의 입금 완료 등)

- **경로**: `POST /webhooks/payments` (로그인 없이 호출되며 사이트 간 요청 위조 방어에서 제외하되 서명으로 인증한다)
- **인증**: 대행사가 주는 서명이나 비밀 값으로 검증한다. 검증에 실패하면 400으로 거절하고 아무 것도 바꾸지 않는다.
- **멱등**: 이벤트 식별자를 멱등키로 쓴다. 같은 이벤트가 여러 번 와도 한 번만 처리한다.
- **응답**: **처리가 완료된 뒤에만 200**을 준다. 처리 중 오류가 나면 5xx로 응답해 대행사가 다시 보내게 하고, 멱등키를 처리 중으로 남기지 않는다(점유 만료로 회수한다). 이미 처리된 중복 이벤트에는 저장된 결과로 200을 준다.
- **검증**: 웹훅 본문을 믿지 않고 `query`로 상태와 금액을 다시 확인한 뒤 반영한다.
- **기한 후 입금과 만료 뒤 성공**: 결제 만료로 이미 취소됨인 주문(고객이 직접 취소한 결제 대기 주문 포함)에 승인이나 입금이 `query`로 확인되면 결제를 만료 → 성공으로 기록하고 주문을 취소됨 → "확인 필요"(사유 기록)로 바꾼 뒤 **자동 전액 환불**을 요청한다. 재고 확보 만료 뒤 성공(주문이 아직 결제 대기)은 결제 대기 → 확인 필요로 같은 흐름을 따른다. 어느 경우에도 주문을 확정하지 않는다. 금액이 주문 총액과 다르면 사유를 금액 불일치로 기록한다.

## 테스트용 가짜 구현이 지원해야 할 시나리오

성공, 실패, 시간 초과(결과 모름), 같은 멱등키 재시도, 금액 불일치, 웹훅 중복, 웹훅 서명 오류, 기한 후 입금, **환불 실패, 환불 결과 모름(시간 초과 뒤 조회로 완료·실패 확인), 만료 뒤 성공(만료 → 성공, 확인 필요 → 자동 전액 환불), 점유 만료된 키(처리 중에 죽은 요청을 다른 요청이 이어받음), 웹훅 처리 중 오류(5xx 응답과 재전송), 가상계좌 환불 계좌 누락**.
