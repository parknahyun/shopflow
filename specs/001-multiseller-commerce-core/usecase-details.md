**근거 문서**: [spec.md](spec.md), [data-model.md](data-model.md), [contracts/web-routes.md](contracts/web-routes.md), [contracts/payment-gateway-port.md](contracts/payment-gateway-port.md)

**결정 문서**: [ADR-0009](../../docs/adr/0009-review-decisions-payment-refund-scope.md)

이 문서의 "화면"과 "버튼"은 별도 프론트엔드가 보여 줄 내용을 뜻한다. 백엔드는 REST API만 제공한다.

## 공통 규칙

모든 유즈케이스에 아래 규칙이 적용된다. 각 유즈케이스에서는 반복하지 않는다.

- **로그인**: 방문자용 유즈케이스(UC-01, UC-02, UC-09)를 제외하면 모두 해당 계정 유형으로 로그인해야 한다(UC-23은 입점 상태와 관계없이 판매자 계정으로 로그인한다). 로그인하지 않았거나 계정 유형이 맞지 않으면 접근이 거절된다. 고객 계정은 판매 기능을, 판매자 계정은 장바구니와 주문 기능을 쓸 수 없다(FR-002a).
- **권한 없는 조회**: 다른 고객의 주문이나 다른 판매자의 하위 주문에 접근하면 존재 여부를 알리지 않고 "찾을 수 없음"으로 응답한다(FR-004, FR-014).
- **멱등 처리**: 결제, 취소·환불, 웹훅 요청은 중복 방지 식별값을 가진다. 같은 값의 요청은 한 번만 처리하고 같은 결과를 돌려준다(FR-009, FR-013b). 식별값은 시도마다 새로 만들며 실패한 결과도 저장하고, 재시도는 새 식별값을 쓴다. 처리 중인 식별값은 점유 시간이 지나면 다른 요청이 대행사 조회로 상태를 확인해 이어받는다.
- **환불 기록**: 환불은 취소(상태 변경)와 같은 트랜잭션에서 "요청"으로 먼저 기록한 뒤 대행사를 호출한다. 하위 주문 하나에 완료되거나 진행 중인 환불은 하나뿐이다.
- **변경 이력**: 결제, 주문, 하위 주문, 재고 확보의 상태가 바뀔 때마다 이력을 추가한다. 수정과 삭제는 하지 않는다(FR-016).
- **정보 보호**: 카드번호 원문은 저장하거나 기록하지 않고, 개인정보는 기록에 남기지 않는다(FR-015).
- **화면 문구**: 모든 안내 문구는 한글로 쉽게 쓴다.

## 액터

| 액터 | 설명 |
|------|------|
| 방문자 | 로그인하지 않은 사용자. 상품을 보고 가입할 수 있다. |
| 고객 | 로그인한 구매자. 방문자의 모든 기능을 쓸 수 있다. |
| 판매자 | 판매 계정. 고객 계정과 별개다. 입점이 승인되어야 판매할 수 있고, 거절된 판매자도 로그인해 자기 입점 상태를 볼 수 있다. |
| 운영자 | 입점 신청을 심사하고 확인 필요 주문과 문제 신고된 하위 주문을 조회한다. |
| 결제 대행사 | 외부 시스템. 결제 승인, 입금 확인, 환불을 처리한다. |
| 시간 기반 처리 | 정해진 시각에 자동으로 실행되는 시스템 작업. |

## 탐색과 가입

### UC-01 상품 탐색·검색

- **주 액터**: 방문자, 고객
- **목적**: 판매 중인 상품을 찾아보고 상세 정보와 옵션별 재고 상태를 확인한다.
- **사전 조건**: 없음(로그인 불필요).
- **사후 조건**: 데이터가 바뀌지 않는다.
- **기본 흐름**:
  1. 사용자가 상품 목록을 연다.
  2. 시스템이 판매 중이고 승인된 판매자의 상품만 보여 준다.
  3. 사용자가 이름의 일부로 검색하거나 판매자별로 모아 본다.
  4. 사용자가 상품을 선택하면 시스템이 상세와 옵션 조합별 선택 가능 여부를 보여 준다.
- **대안 흐름**:
  - 3a. 검색 결과가 없으면 "결과가 없습니다" 안내를 보여 준다.
  - 4a. 특정 옵션 조합이 품절이면 그 조합만 선택할 수 없게 표시하고 나머지는 선택할 수 있다. 모든 조합이 품절이면 상품을 품절로 표시하고 담기를 막는다.
- **예외 흐름**: 판매 중지, 거절, 정지 상태의 판매자 상품 주소로 직접 들어오면 "찾을 수 없음"으로 응답한다.
- **업무 규칙**: 판매자 정지·거절과 상품 판매 중지는 목록과 검색에서 즉시 반영된다.

### UC-02 고객 가입

- **주 액터**: 방문자
- **목적**: 구매할 수 있도록 고객 계정을 만든다.
- **사전 조건**: 로그인하지 않은 상태.
- **사후 조건**: 고객 계정이 만들어지고 로그인할 수 있다.
- **기본 흐름**:
  1. 방문자가 이메일과 비밀번호를 입력한다.
  2. 시스템이 입력값을 서버에서 검증한다.
  3. 시스템이 비밀번호를 솔트가 적용된 해시로 저장하고 계정을 만든다.
  4. 시스템이 로그인 화면으로 안내한다.
- **대안 흐름**: 없음.
- **예외 흐름**:
  - 2a. 이미 가입된 이메일이면 "이미 가입된 이메일입니다"를 안내하고 계정을 만들지 않는다.
  - 2b. 이메일 형식이나 비밀번호 규칙이 맞지 않으면 항목별로 고칠 점을 안내한다.
- **업무 규칙**: 계정 유형별로 이메일이 유일하다. 같은 이메일로 판매자 계정을 따로 만들 수 있다(계획 문서의 결정).

## 구매

### UC-03 장바구니 관리

- **주 액터**: 고객
- **목적**: 여러 판매자의 상품을 옵션 조합을 골라 한 장바구니에 모은다.
- **사전 조건**: 고객으로 로그인했다.
- **사후 조건**: 장바구니 항목이 추가, 변경, 삭제된다. 재고는 바뀌지 않는다(재고는 결제를 시작할 때 확보한다).
- **기본 흐름**:
  1. 고객이 상품 상세에서 옵션 조합과 수량을 정해 담는다.
  2. 시스템이 판매 중인지와 수량이 1 이상인지 확인하고 항목을 추가한다.
  3. 고객이 장바구니에서 수량을 바꾸거나 항목을 뺀다.
- **대안 흐름**: 3a. 같은 옵션 조합을 다시 담으면 새 항목을 만들지 않고 수량을 합친다.
- **예외 흐름**:
  - 2a. 상품이 판매 중지되었거나 옵션 조합이 품절이면 담을 수 없다고 안내한다.
  - 장바구니를 열 때 담아 둔 상품이 판매 중지되었거나 가격이 바뀌었으면 해당 항목에 변경 내용을 표시한다.
- **업무 규칙**: (고객, 판매 단위)가 유일하다. 수량이 재고보다 많으면 주문을 시작할 수 없다.

### UC-04 즉시 결제로 주문

- **주 액터**: 고객
- **보조 액터**: 결제 대행사
- **목적**: 장바구니의 상품을 카드 등 즉시 결제로 한 번에 주문한다. 재고 선점과 결제 검증이 이 유즈케이스 안에서 함께 처리된다.
- **사전 조건**: 고객으로 로그인했고 장바구니에 항목이 있다. 고객의 결제 대기 주문이 상한(기본 3건, 설정값)보다 적다.
- **사후 조건(성공)**: 결제가 성공으로 기록되고, 주문이 확정되며, 결제 시작 때 만든 판매자별 하위 주문(발송 전)이 판매자에게 보이게 되고, 재고 확보가 확정된다.
- **사후 조건(실패)**: 주문과 하위 주문이 취소가 되고, 재고가 반환되며, 결제는 청구되지 않는다.
- **사후 조건(확인 필요)**: 결제는 성공했지만 주문을 확정할 수 없으면 주문이 "확인 필요"가 되고 UC-24가 전액 자동 환불한다.
- **기본 흐름**:
  1. 고객이 주문 확인 화면에서 상품, 금액, 배송지를 확인하고 결제 방식으로 즉시 결제를 고른다.
  2. 고객이 "결제하기"를 누른다. 요청에 고객이 확인한 금액과 이 시도의 중복 방지 식별값이 붙는다.
  3. 시스템이 고객이 확인한 금액을 서버가 계산한 주문 총액과 대조하고, 결제 대기 주문 수와 판매 단위별 수량(기본 10개) 상한을 확인한다.
  4. 시스템이 한 트랜잭션에서 모든 상품의 재고를 판매 단위별로 확보하고(차감), 주문(결제 대기), 판매자별 하위 주문, 결제(준비)를 만든다.
  5. 시스템이 결제 대행사에 결제를 준비하고 고객을 결제창으로 보낸다.
  6. 고객이 결제창에서 결제를 마치고 돌아온다. 돌아온 경로(성공, 실패)는 읽기 전용이며 아무것도 바꾸지 않는다.
  7. 프론트엔드가 결과 확인 요청(POST, 중복 방지 식별값 포함)을 보내면, 시스템이 결제 대행사에 결과를 직접 조회해 상태, 주문 번호, 금액을 서버에 저장된 주문 총액과 대조한다. 확정과 재고 반환은 이 조회 결과로만 한다.
  8. 일치하면 결제를 성공으로, 재고 확보를 확정으로, 주문을 확정으로 바꾼다.
  9. 시스템이 주문 완료 정보에 판매자별 하위 주문을 담아 돌려준다.
- **대안 흐름**:
  - 2a. 같은 식별값의 요청이 이미 처리되었으면 저장된 결과를 그대로 돌려주고 새로 처리하지 않는다.
  - 6a. 고객이 결제창을 닫거나 같은 요청을 여러 번 보내도 결제는 한 번만 일어난다.
  - 결제가 실패한 뒤 다시 결제하려면 새 시도로 새 식별값을 쓴다.
  - 결제를 끝내기 전에 고객이 주문을 직접 취소할 수 있다(UC-20).
- **예외 흐름**:
  - 3a. 고객이 확인한 금액이 서버 계산값과 다르면 결제를 시작하지 않고, 달라졌다고 안내하며 새 금액으로 다시 확인하게 한다.
  - 3b. 결제 대기 주문이 상한이면 결제를 시작하지 않고 기존 결제 대기 주문을 먼저 취소하라고 안내한다(UC-20). 판매 단위별 수량이 상한을 넘어도 시작하지 않는다.
  - 4a. 재고가 하나라도 부족하면 전체를 되돌리고 부족한 상품을 안내한다. 다른 고객이 결제 중이어서 확보된 재고는 살 수 없다.
  - 7a. 대행사 결제가 실패하면 재고를 반환하고 주문을 취소됨으로, 하위 주문을 취소로 바꾼 뒤 실패를 안내한다.
  - 7b. 금액이나 주문 번호가 맞지 않으면 확정하지 않고 오류로 기록하며, 이미 대행사에서 승인되었다면 "확인 필요"(사유: 금액 불일치)로 두고 UC-24가 전액 환불한다.
  - 7c. 대행사 호출이 시간 초과로 끝나 결과를 알 수 없으면, 조회로 확인하기 전까지 재고를 반환하지 않는다. 확인 결과 승인되었다면 8단계로 이어지고, 이미 재고 확보가 만료되어 주문이 취소된 뒤라면 7d를 따른다.
  - 7d. 결제는 성공했는데 재고 확보 유지 시간이 이미 지났으면(만료로 취소된 뒤 승인이 확인된 경우 포함) 주문을 확정하지 않고 "확인 필요"(사유: 재고 확보 만료 뒤 결제 성공)로 기록한다. 하위 주문은 판매자에게 보이지 않는다. 시스템은 UC-24로 결제 금액을 자동 전액 환불한다. 환불이 끝나면 주문은 "환불됨"이 된다.
  - 결제가 끝나지 않고 유지 시간(기본 15분)이 지나면 UC-17이 재고를 반환한다. 만료 처리 전에 항상 대행사에 먼저 조회한다.
- **업무 규칙**: 카드번호는 서버를 지나가지 않는다. 결제 결과는 클라이언트 값을 믿지 않고 서버가 직접 조회한다. 한 주문에 성공 결제는 하나뿐이고, 주문당 진행 중(준비, 승인 대기, 입금 대기)인 결제는 하나뿐이다. 하위 주문 항목에는 주문 당시 단가를 복사해 둔다. 하위 주문은 결제 시작 때 만들고 주문이 확정되기 전에는 판매자에게 보이지 않는다(FR-011, FR-011a). 정지된 판매자의 상품은 주문할 수 없다.

### UC-05 입금 대기로 주문

- **주 액터**: 고객
- **보조 액터**: 결제 대행사
- **목적**: 가상계좌로 입금하는 방식으로 주문한다. 입금 기한 동안 재고를 확보해 둔다.
- **사전 조건**: UC-04의 사전 조건과 같다.
- **사후 조건(입금 완료)**: UC-04의 성공 사후 조건과 같다.
- **사후 조건(기한 만료)**: UC-18이 주문과 하위 주문을 취소하고 재고를 반환한다.
- **사후 조건(기한 후 입금)**: 주문이 "확인 필요"가 되고 UC-24가 입금액을 전액 환불한다.
- **기본 흐름**:
  1. UC-04의 1~4 단계를 따르되 결제 방식으로 입금 대기를 고르고, 환불 계좌(은행, 계좌번호, 예금주)를 함께 입력한다. 재고 확보 만료 시각은 입금 기한(기본 24시간)으로 정해진다.
  2. 시스템이 환불 계좌의 계좌번호를 암호화해 저장하고(기록에는 남기지 않는다), 대행사에 가상계좌 발급을 요청해 은행, 계좌번호, 입금 기한을 고객에게 안내한다. 주문은 결제 대기, 결제는 입금 대기 상태다.
  3. 고객이 기한 안에 입금한다.
  4. 대행사가 입금 완료 알림(웹훅)을 보낸다. 시스템이 서명을 검증하고 이벤트 식별자로 중복을 걸러낸다.
  5. 시스템이 대행사에 상태와 금액을 다시 조회해 확인한 뒤 결제를 성공으로, 재고 확보를 확정으로, 주문을 확정으로 바꾼다.
  6. 처리가 모두 끝난 뒤에만 웹훅에 정상(200) 응답을 보낸다.
- **대안 흐름**:
  - 4a. 같은 알림이 여러 번 와도 한 번만 처리하고 항상 정상 응답한다.
  - 입금 전에 고객이 주문을 직접 취소할 수 있다(UC-20). 이때 결제 수단을 바꾸려면 취소하고 다시 주문한다.
- **예외 흐름**:
  - 1a. 환불 계좌가 빠지면 결제를 시작하지 않고 입력을 요구한다.
  - 4b. 알림의 서명 검증에 실패하면 거절하고 아무것도 바꾸지 않는다.
  - 4c. 알림을 처리하다 오류가 나면 5xx로 응답해 대행사가 다시 보내게 하고, 식별값을 처리 중으로 남기지 않는다.
  - 5a. 입금 기한이 지난 뒤에 입금이 들어오면(만료로 취소된 뒤 입금이 확인된 경우 포함) 주문을 확정하지 않고 "확인 필요"(사유: 기한 후 입금)로 기록하고 UC-24가 환불 계좌로 전액 환불한다.
  - 5b. 입금 금액이 주문 총액과 다르면 확정하지 않고 "확인 필요"(사유: 금액 불일치)로 기록하며 UC-24가 입금액 전액을 환불한다.
  - UC-04의 3a, 3b, 4a 예외는 같은 방식으로 적용한다.
- **업무 규칙**: 입금 대기 중인 재고는 다른 고객이 살 수 없다. 입금 기한은 운영 설정으로 바꿀 수 있다. 환불 계좌는 개인정보이므로 암호화해 저장하고 로그에 남기지 않으며 환불이 끝나면 가린다(FR-015, FR-019). 대행사별 환불 계좌 요구 사양은 구현 전에 확인한다.

### UC-06 내 주문 조회

- **주 액터**: 고객
- **목적**: 내 주문과 하위 주문별 배송 상태를 확인한다.
- **사전 조건**: 고객으로 로그인했다.
- **사후 조건**: 데이터가 바뀌지 않는다.
- **기본 흐름**:
  1. 고객이 주문 목록을 연다. 시스템이 본인의 주문만 보여 준다.
  2. 고객이 주문을 선택하면 시스템이 주문 상태(결제 대기, 확정, 취소됨, 확인 필요, 환불됨), 전체 금액과 판매자별 하위 주문의 상태(발송 전, 배송 중, 배송 완료, 구매 확정, 취소), 송장 정보, 환불 진행 상태를 보여 준다.
- **대안 흐름**: 2a. 주문과 하위 주문 상태에 따라 가능한 행동(결제 대기 주문 취소, 하위 주문 취소, 구매 확정, 문제 신고)만 보여 준다. 문제 신고한 하위 주문은 신고 접수 표시가 붙는다.
- **예외 흐름**: 다른 고객의 주문 주소로 들어오면 "찾을 수 없음"으로 응답한다.
- **업무 규칙**: 판매자가 발송 처리하면 1분 안에 고객 화면에 반영된다(SC-007).

### UC-07 발송 전 하위 주문 취소

- **주 액터**: 고객
- **보조 액터**: 결제 대행사
- **목적**: 판매자가 발송하기 전에 하위 주문을 취소하고 전액 환불받는다.
- **사전 조건**: 고객으로 로그인했고, 본인 주문(확정된 주문)의 하위 주문이 "발송 전" 상태다.
- **사후 조건**: 하위 주문이 취소가 되고(취소 주체: 고객), 해당 항목의 재고가 돌아오고, 하위 주문 금액이 전액 환불되며, 환불 거래 내역이 추가된다.
- **기본 흐름**:
  1. 고객이 하위 주문에서 "취소"를 누른다. 요청에 중복 방지 식별값이 붙는다.
  2. 시스템이 한 트랜잭션에서 하위 주문이 발송 전인지 조건부로 확인하면서 상태를 취소로 바꾸고, 재고를 판매 단위별로 한 번만 더하고, 환불을 "요청"으로 기록한다.
  3. 시스템이 대행사에 하위 주문 금액만큼 환불을 요청한다.
  4. 환불이 성공하면 환불을 완료로 바꾸고 환불 거래 내역을 추가한 뒤 고객에게 안내한다.
- **대안 흐름**:
  - 한 주문에 여러 판매자의 하위 주문이 있으면 취소한 하위 주문의 금액만 환불하고 나머지는 그대로 진행한다.
  - 모든 하위 주문이 취소가 되면 주문도 취소됨으로 본다.
- **예외 흐름**:
  - 2a. 이미 배송 중이거나 그 이후 상태면 "발송된 주문은 취소할 수 없습니다"를 안내한다.
  - 2b. 고객의 취소와 판매자의 발송 처리가 동시에 들어오면 먼저 처리된 요청만 반영하고 다른 요청은 거절한다.
  - 2c. 주문이 아직 결제 대기이면 하위 주문 단독 취소는 거절한다. 주문 단위로 취소한다(UC-20).
  - 1a. 같은 취소 요청이 여러 번 들어와도 환불은 한 번만 일어난다.
  - 3a. 대행사 환불이 실패하거나 결과를 알 수 없으면 환불을 "확인 중" 또는 "실패"로 기록하고 UC-25가 조회와 재시도로 이어 간다. 이 경우 고객에게 처리 중임을 안내한다. 취소와 재고 반환은 이미 끝났으므로 되돌리지 않는다.
- **업무 규칙**: 환불은 하위 주문 금액 전액만 다룬다. 하위 주문별 환불 합계는 그 금액을 넘을 수 없고, 하위 주문 하나에 완료되거나 진행 중인 환불은 하나뿐이다. 취소 수수료는 없다. 가상계좌 결제는 결제 시작 때 받은 환불 계좌로 환불한다. 부분 환불과 발송 후 반품 환불은 이번 범위에서 제외한다(FR-017). 취소는 주문이 확정된 뒤에만 할 수 있다(FR-011a, FR-013a).

### UC-08 구매 확정

- **주 액터**: 고객
- **목적**: 상품을 받은 뒤 구매를 확정한다. 이 시각이 이후 정산의 기준이 된다.
- **사전 조건**: 고객으로 로그인했고, 본인 주문의 하위 주문이 "배송 완료" 상태다.
- **사후 조건**: 하위 주문이 구매 확정이 되고 구매 확정 시각이 기록된다.
- **기본 흐름**:
  1. 고객이 배송 완료된 하위 주문에서 "구매 확정"을 누른다.
  2. 시스템이 조건부로 상태를 구매 확정으로 바꾸고 시각을 기록한다.
  3. 시스템이 확정 완료를 안내한다.
- **대안 흐름**: 고객이 누르지 않으면 UC-19가 7일 뒤 자동으로 확정한다.
- **예외 흐름**: 배송 완료 상태가 아니거나 이미 구매 확정, 취소인 하위 주문이면 허용되지 않는 변경으로 거절한다.
- **업무 규칙**: 구매 확정 이후에는 상태를 바꿀 수 없다. 문제 신고(UC-22)를 한 하위 주문은 자동 구매 확정에서 빠진다(UC-19). 신고 뒤 고객의 직접 구매 확정을 허용할지는 신고 처리 기능에서 정한다.

### UC-20 결제 대기 주문 취소

- **주 액터**: 고객
- **보조 액터**: 결제 대행사
- **목적**: 결제를 끝내지 않은 주문을 직접 취소해 재고를 돌려주고, 결제 수단이나 주문 내용을 바꿔 다시 주문할 수 있게 한다.
- **사전 조건**: 고객으로 로그인했고, 본인의 주문이 "결제 대기" 상태다.
- **사후 조건**: 주문이 취소됨, 하위 주문이 취소(취소 주체: 고객), 재고 확보가 반환, 결제가 만료가 되고 재고가 돌아온다.
- **기본 흐름**:
  1. 고객이 결제 대기 주문에서 "주문 취소"를 누른다. 요청에 중복 방지 식별값이 붙는다.
  2. 시스템이 결제가 승인 대기나 입금 대기이면 만료 처리 전에 대행사에 먼저 조회해, 아직 승인이나 입금이 없음을 확인한다.
  3. 시스템이 한 트랜잭션에서 주문이 결제 대기인지 조건부로 확인하면서 주문을 취소됨으로, 하위 주문을 취소로, 결제를 만료로, 재고 확보를 반환으로 바꾸고 재고를 한 번만 더한다.
  4. 시스템이 취소 완료를 안내한다. 고객은 필요하면 새로 주문한다.
- **대안 흐름**: 4a. 결제 수단을 바꾸고 싶으면 이 유즈케이스로 취소한 뒤 UC-04나 UC-05로 다시 주문한다. 취소하면 결제 대기 주문 수가 줄어 상한(UC-04의 3b)에 걸린 고객도 새로 시작할 수 있다.
- **예외 흐름**:
  - 1a. 같은 취소 요청이 여러 번 들어와도 한 번만 처리하고 같은 결과를 돌려준다.
  - 2a. 조회 결과 이미 승인되었거나 입금되었으면 취소하지 않고 UC-04나 UC-05의 결과 처리를 따른다(재고 확보 유지 중이면 주문 확정, 만료 뒤이면 "확인 필요"). 확정된 주문을 취소하려면 UC-07을 쓴다.
  - 3a. 주문이 이미 결제 대기가 아니면(확정, 취소됨, 확인 필요, 환불됨) 거절하고 현재 상태를 안내한다.
  - 하위 주문 하나만 취소하려 하면 거절한다(UC-07의 2c).
- **업무 규칙**: 결제 대기 주문의 취소는 주문 단위만 있다(FR-018). 결제 대기에서는 아직 청구된 금액이 없으므로 보통 환불이 없다. 취소 직전에 승인이 확인된 경우는 2a와 UC-24를 따른다. 다른 고객의 주문은 "찾을 수 없음"으로 응답한다.

### UC-22 문제 신고

- **주 액터**: 고객
- **목적**: 배송 완료된 상품에 문제가 있을 때 구매 확정 전에 알리고, 자동 구매 확정에서 빼서 확정 기회를 잃지 않게 한다.
- **사전 조건**: 고객으로 로그인했고, 본인 주문의 하위 주문이 "배송 완료" 상태이며 구매 확정 전이다.
- **사후 조건**: 하위 주문에 문제 신고 시각과 신고 사유가 기록된다. 상태는 배송 완료 그대로이며 자동 구매 확정 대상에서 빠진다.
- **기본 흐름**:
  1. 고객이 배송 완료된 하위 주문에서 "문제 신고"를 누르고 사유를 적는다.
  2. 시스템이 하위 주문이 배송 완료이고 아직 신고되지 않았는지 조건부로 확인하며 신고 시각과 사유를 기록하고 이력을 남긴다.
  3. 시스템이 신고 접수를 안내한다.
- **대안 흐름**: 운영자는 UC-16에서 신고된 하위 주문을 조회한다.
- **예외 흐름**:
  - 1a. 사유가 비어 있으면 입력을 요구한다.
  - 2a. 배송 완료가 아니거나 이미 구매 확정, 취소된 하위 주문이면 신고할 수 없다고 거절한다.
  - 2b. 같은 하위 주문을 이미 신고했으면 새로 만들지 않고 기존 신고를 알려 준다.
  - 신고와 자동 구매 확정이 동시에 들어오면 먼저 처리된 것만 반영한다.
  - 다른 고객의 하위 주문이면 "찾을 수 없음"으로 응답한다.
- **업무 규칙**: 신고의 처리(환불, 반품, 분쟁 중재)는 이번 범위에 없고 표시와 조회만 한다(FR-020, FR-017). 신고 가능 기간은 구매 확정 전까지이며 별도 기간 값은 계획 단계에서 정한다.

## 판매

### UC-09 판매자 가입·입점 신청

- **주 액터**: 판매자(가입 전 방문자)
- **목적**: 판매자 계정을 만들고 사업자 정보와 증빙 서류를 내어 입점을 신청한다.
- **사전 조건**: 로그인하지 않은 상태.
- **사후 조건**: 판매자 계정, 판매자 정보(상태: 신청), 입점 서류가 만들어진다.
- **기본 흐름**:
  1. 판매자가 이메일과 비밀번호를 입력한다.
  2. 판매자가 사업자 유형(개인사업자 또는 법인사업자)을 고른다.
  3. 판매자가 공통 정보(상호명, 사업자등록번호, 대표자명, 연락처, 사업장 주소, 통신판매업 신고번호)를 입력하고, 법인사업자는 법인명과 법인등록번호를 더 입력한다.
  4. 판매자가 사업자등록증 사본을 올린다.
  5. 시스템이 입력값과 서류를 검증하고 판매자 계정, 판매자 정보(상태: 신청), 입점 서류를 한 번에 만든다.
  6. 시스템이 "운영자 승인 후 판매할 수 있습니다"를 안내한다.
- **대안 흐름**: 없음.
- **예외 흐름**:
  - 같은 유형의 이메일이 이미 있으면 가입을 거절하고 안내한다.
  - 5a. 사업자등록번호가 이미 등록되어 있으면 "이미 등록된 사업자입니다"를 안내하고 접수하지 않는다.
  - 5b. 사업자 유형에 필요한 항목이나 서류가 빠지면 빠진 항목을 안내하고 접수하지 않는다.
  - 5c. 서류가 허용 형식이나 크기를 넘으면 거절한다.
- **업무 규칙**: 승인 전에는 상품을 등록할 수 없다. 대표자 주민등록번호는 받지 않는다. 입점 서류는 판매자 본인과 운영자만 볼 수 있다(FR-002d). 사업자 등록이 없는 개인은 입점할 수 없다(FR-002c). 거절된 뒤의 재신청은 UC-23에서 한다.

### UC-10 상품·옵션·재고 등록과 수정

- **주 액터**: 판매자
- **목적**: 상품과 옵션 조합별 가격, 재고를 등록하고 고친다.
- **사전 조건**: 입점이 승인된 판매자로 로그인했다. 정지된 판매자는 새 상품을 등록할 수 없다(FR-002f).
- **사후 조건**: 상품과 판매 단위가 저장되고, 판매 중이면 고객 목록에 보인다.
- **기본 흐름**:
  1. 판매자가 상품 이름, 설명, 사진을 입력한다.
  2. 판매자가 옵션(예: 색상, 사이즈)을 정하고, 옵션 조합마다 가격과 재고 수량을 입력한다. 옵션이 없으면 판매 단위 하나만 입력한다.
  3. 시스템이 입력값을 검증하고 저장한다.
  4. 판매자가 나중에 상품 정보, 가격, 재고를 수정한다. 재고는 "총 보유 수량"으로 입력한다.
  5. 시스템이 결제 중으로 묶인 수량과 판매된 수량을 뺀 가용 수량을 계산해 버전 검사와 함께 반영하고, 계산된 가용 수량을 보여 준다.
- **대안 흐름**: 4a. 재고를 고치는 동안 결제 중인 주문이 있으면, 이미 확보된 수량은 건드리지 않고 가용 수량만 바뀐다.
- **예외 흐름**:
  - 1a. 필수 정보가 없거나 가격이 0 이하이거나 재고가 음수면 항목별로 안내하고 저장하지 않는다.
  - 5a. 입력한 총 보유 수량이 묶인 수량과 판매된 수량의 합보다 작아 가용 수량이 음수가 되면 거절하고 안내한다.
  - 5b. 같은 판매 단위를 동시에 고쳐 버전이 어긋나면 나중 요청을 거절하고 새로 불러와 다시 입력하게 한다.
  - 1b. 사진이 허용 형식이나 크기를 넘으면 거절한다.
  - 승인 전, 거절, 정지 상태의 판매자는 등록할 수 없다고 안내한다.
  - 다른 판매자의 상품을 고치려 하면 "찾을 수 없음"으로 응답한다.
- **업무 규칙**: 한 상품 안에서 옵션 조합은 중복될 수 없다. 이미 만들어진 주문의 단가는 가격을 바꿔도 달라지지 않는다.

### UC-11 상품 판매 중지

- **주 액터**: 판매자
- **목적**: 상품을 더 이상 팔지 않도록 내린다.
- **사전 조건**: 입점이 승인된 판매자로 로그인했고, 본인의 판매 중인 상품이 있다.
- **사후 조건**: 상품의 판매 상태가 판매 중지가 된다.
- **기본 흐름**:
  1. 판매자가 상품에서 "판매 중지"를 누른다.
  2. 시스템이 상태를 바꾸고 고객 목록과 검색에서 뺀다.
- **대안 흐름**: 이미 결제가 끝난 주문은 영향을 받지 않고 계속 진행한다.
- **예외 흐름**: 장바구니에 담긴 중지 상품은 고객이 주문할 수 없고, 장바구니에서 "구매할 수 없음"으로 표시된다. 결제 중이어서 이미 재고가 확보된 주문은 결제를 마칠 수 있다.
- **업무 규칙**: 판매 중지는 되돌릴 수 있다(상품 수정에서 다시 판매).

### UC-12 내 하위 주문 조회

- **주 액터**: 판매자
- **목적**: 내 상품이 포함된 하위 주문만 보고 처리할 일을 확인한다.
- **사전 조건**: 판매자로 로그인했고 입점이 승인되었거나 정지 상태다(정지된 판매자는 이미 확정된 주문의 하위 주문만 본다. FR-002f).
- **사후 조건**: 데이터가 바뀌지 않는다.
- **기본 흐름**:
  1. 판매자가 하위 주문 목록을 연다. 시스템이 본인 판매자 식별자로 걸러, 주문이 확정된 하위 주문만 보여 준다.
  2. 판매자가 하위 주문을 선택하면 상품, 옵션, 수량, 배송지, 상태를 본다.
- **대안 흐름**: 상태별로 걸러 보기(발송 전, 배송 중 등)를 할 수 있다. 확정된 뒤 정해진 기간 안에 발송하지 않은 하위 주문에는 발송 지연 표시가 붙는다(자동 취소는 하지 않는다. FR-013c).
- **예외 흐름**: 다른 판매자의 하위 주문 주소로 들어오면 "찾을 수 없음"으로 응답한다.
- **업무 규칙**: 주문이 확정되지 않은(결제 대기, 취소됨, 확인 필요, 환불됨) 주문의 하위 주문은 보이지 않는다(FR-011a). 같은 주문의 다른 판매자 하위 주문 내용은 보이지 않는다. 판매자의 접근 제한은 서버 권한 검사로 강제한다.

### UC-13 송장 입력

- **주 액터**: 판매자
- **목적**: 상품을 보내고 송장 정보를 입력해 하위 주문을 배송 중으로 바꾼다.
- **사전 조건**: 본인 하위 주문이 "발송 전" 상태이고 속한 주문이 확정되었다. 판매자의 입점이 정지 상태여도 가능하다(FR-002f).
- **사후 조건**: 하위 주문이 배송 중이 되고 송장 정보가 저장된다. 다른 판매자의 하위 주문은 그대로다.
- **기본 흐름**:
  1. 판매자가 하위 주문에서 택배사와 송장 번호를 입력한다.
  2. 시스템이 조건부로 상태를 "발송 전"에서 "배송 중"으로 바꾸고 송장 정보를 저장한다.
  3. 고객 화면에 배송 중과 송장 정보가 보인다.
- **대안 흐름**: 같은 주문의 다른 판매자는 각자 따로 발송 처리한다.
- **예외 흐름**:
  - 2a. 하위 주문이 이미 취소되었으면 "취소된 주문입니다"를 안내하고 거절한다(UC-07, UC-21과 동시에 들어오면 먼저 처리된 것만 반영).
  - 허용되지 않는 상태 변경(예: 배송 완료 후 되돌리기)은 거절한다.
  - 송장 번호가 비어 있으면 입력을 요구한다.
- **업무 규칙**: 택배사 연동은 이번 범위에서 제외하며 송장 정보는 판매자가 직접 입력한다.

### UC-14 배송 완료 처리

- **주 액터**: 판매자
- **목적**: 상품이 고객에게 도착했을 때 하위 주문을 배송 완료로 바꾼다.
- **사전 조건**: 본인 하위 주문이 "배송 중" 상태다. 판매자의 입점이 정지 상태여도 가능하다(FR-002f).
- **사후 조건**: 하위 주문이 배송 완료가 되고 배송 완료 시각이 기록된다. 아직 구매 확정은 아니다.
- **기본 흐름**:
  1. 판매자가 하위 주문에서 "배송 완료"를 누른다.
  2. 시스템이 조건부로 상태를 바꾸고 시각을 기록한다.
  3. 고객 화면에 배송 완료와 구매 확정 버튼이 보인다.
- **대안 흐름**: 없음.
- **예외 흐름**: 배송 중이 아닌 하위 주문이면 허용되지 않는 변경으로 거절한다. 다른 판매자의 하위 주문이면 "찾을 수 없음"으로 응답한다.
- **업무 규칙**: 판매자가 배송 완료로 바꿔도 정산 기준은 바뀌지 않는다. 구매 확정 시점이 정산 기준이다. 배송 완료 후 7일이 지나면 UC-19가 자동 확정한다(문제 신고된 건은 제외). 배송 완료 시각은 하위 주문이 복사해 가지며 자동 확정의 기준이다.

### UC-21 판매자 직접 취소

- **주 액터**: 판매자
- **보조 액터**: 결제 대행사
- **목적**: 재고 부족이나 판매 불가 같은 사정으로 발송할 수 없는 하위 주문을 발송 전에 취소하고 고객에게 전액 환불한다.
- **사전 조건**: 판매자로 로그인했고(입점이 정지된 판매자도 가능, FR-002f), 본인의 하위 주문이 "발송 전"이며 속한 주문이 확정되었다.
- **사후 조건**: 하위 주문이 취소가 되고(취소 주체: 판매자, 사유 기록), 해당 항목의 재고가 돌아오고, 하위 주문 금액이 전액 환불된다.
- **기본 흐름**:
  1. 판매자가 하위 주문에서 "취소"를 누르고 사유를 적는다. 요청에 중복 방지 식별값이 붙는다.
  2. 시스템이 한 트랜잭션에서 하위 주문이 발송 전인지 조건부로 확인하면서 상태를 취소로 바꾸고, 취소 주체와 사유를 기록하고, 재고를 판매 단위별로 한 번만 더하고, 환불(사유: 판매자 취소)을 "요청"으로 기록한다.
  3. 시스템이 대행사에 하위 주문 금액만큼 환불을 요청한다(가상계좌 결제는 환불 계좌 사용).
  4. 환불이 성공하면 환불을 완료로 바꾸고 환불 거래 내역을 추가한다.
- **대안 흐름**: 한 주문에 여러 판매자의 하위 주문이 있으면 취소한 하위 주문의 금액만 환불하고 나머지는 그대로 진행한다. 모든 하위 주문이 취소가 되면 주문도 취소됨으로 본다.
- **예외 흐름**:
  - 1a. 사유가 비어 있으면 취소하지 않고 사유를 요구한다.
  - 2a. 이미 배송 중이거나 그 이후 상태면 "발송된 주문은 취소할 수 없습니다"를 안내한다.
  - 2b. 판매자의 취소와 고객의 취소, 판매자의 발송 처리가 동시에 들어오면 먼저 처리된 요청만 반영하고 다른 요청은 거절한다.
  - 2c. 주문이 확정되기 전(결제 대기 등)의 하위 주문은 판매자에게 보이지 않으므로 "찾을 수 없음"으로 응답한다. 다른 판매자의 하위 주문도 같다.
  - 3a. 대행사 환불이 실패하거나 결과를 알 수 없으면 UC-25가 이어서 처리한다.
- **업무 규칙**: 환불과 재고 반환은 고객 취소(UC-07)와 같은 흐름이다. 하위 주문 금액 전액만 다루며 취소 수수료는 없다(FR-013c). 발송 기한을 넘긴 하위 주문의 자동 취소는 이번 범위에 없고 발송 지연 표시만 한다(UC-12).

### UC-23 입점 상태 확인과 재신청

- **주 액터**: 판매자
- **목적**: 신청, 승인, 거절, 정지 같은 자기 입점 상태와 거절 사유를 확인하고, 거절되었으면 고쳐서 다시 신청한다.
- **사전 조건**: 판매자 계정으로 로그인했다(입점 상태와 관계없이).
- **사후 조건**: 조회만 하면 데이터가 바뀌지 않는다. 재신청하면 입점 상태가 "거절"에서 "신청"이 되고 이력이 남는다.
- **기본 흐름**:
  1. 판매자가 내 입점 상태를 연다. 시스템이 입점 상태와, 거절된 경우 운영자가 적은 거절 사유를 보여 준다.
  2. 거절된 판매자가 사유에 맞게 사업자 정보를 고치고 증빙 서류를 다시 올린다.
  3. 판매자가 "다시 신청"을 누른다.
  4. 시스템이 UC-09와 같은 규칙으로 입력값과 서류를 검증하고, 같은 판매자 정보를 고쳐 입점 상태를 "신청"으로 바꾼다.
  5. 시스템이 "운영자 심사 후 판매할 수 있습니다"를 안내한다. 운영자는 UC-15로 다시 심사한다.
- **대안 흐름**: 신청 상태에서도 서류를 다시 올릴 수 있다.
- **예외 흐름**:
  - 4a. 필수 항목이나 서류가 빠지면 빠진 항목을 안내하고 접수하지 않는다.
  - 4b. 사업자등록번호가 다른 판매자와 겹치면 "이미 등록된 사업자입니다"를 안내하고 접수하지 않는다. 같은 판매자 정보를 고쳐 쓰므로 자기 번호와는 충돌하지 않는다.
  - 4c. 입점 상태가 거절이 아니면(승인, 정지) 재신청할 수 없다고 거절한다.
- **업무 규칙**: 거절된 판매자도 로그인해 자기 입점 상태와 거절 사유를 조회할 수 있다(FR-002e). 입점이 승인되기 전에는 상품을 등록할 수 없다. 입점 서류는 판매자 본인과 운영자만 볼 수 있다.

## 운영

### UC-15 입점 승인·거절

- **주 액터**: 운영자
- **목적**: 입점 신청을 심사해 판매 자격을 준다.
- **사전 조건**: 운영자로 로그인했고 입점 상태가 "신청"인 판매자가 있다.
- **사후 조건**: 판매자의 입점 상태가 승인 또는 거절이 된다.
- **기본 흐름**:
  1. 운영자가 입점 신청 목록을 연다.
  2. 운영자가 신청을 선택해 사업자 정보와 입점 서류(사업자등록증 사본)를 확인한다. 서류는 운영자와 판매자 본인만 열 수 있다.
  3. 운영자가 "승인" 또는 "거절"을 누른다. 거절할 때는 거절 사유를 반드시 적는다.
  4. 시스템이 상태를 바꾸고 거절 사유와 이력을 남긴다.
- **대안 흐름**: 승인된 판매자를 나중에 정지할 수 있고, 정지된 판매자를 다시 승인할 수 있다. 정지는 신규 판매만 막는다. 정지 판매자의 상품은 고객에게 보이지 않고 새 상품을 등록할 수 없지만, 이미 확정된 주문의 발송, 배송 완료 처리, 판매자 취소는 계속할 수 있다(FR-002f).
- **예외 흐름**:
  - 이미 처리된 신청에 다시 처리하려 하면 허용되지 않는 변경으로 거절한다.
  - 3a. 거절 사유가 비어 있으면 거절하지 않고 사유를 요구한다.
- **업무 규칙**: 거절은 종료 상태가 아니다. 거절된 판매자는 UC-23으로 다시 신청할 수 있고, 다시 신청하면 입점 상태가 "신청"이 되어 이 유즈케이스로 다시 심사한다(FR-002e).

### UC-16 확인 필요 주문·문제 신고 조회

- **주 액터**: 운영자
- **목적**: "확인 필요"로 기록된 주문의 자동 환불 진행을 확인하고, 문제 신고된 하위 주문을 확인한다.
- **사전 조건**: 운영자로 로그인했다.
- **사후 조건**: 데이터가 바뀌지 않는다.
- **기본 흐름**:
  1. 운영자가 확인 필요 주문 목록을 연다.
  2. 시스템이 기한 후 입금, 재고 확보 만료 뒤 결제 성공, 금액 불일치로 기록된 주문과 사유, 환불 상태(요청, 확인 중, 완료, 실패), 환불됨 여부를 보여 준다.
  3. 운영자가 문제 신고 목록을 연다. 시스템이 신고된 하위 주문과 신고 시각, 사유를 보여 준다.
- **대안 흐름**: 환불이 계속 실패한 주문은 실패 사유와 함께 걸러 볼 수 있다.
- **예외 흐름**: 없음.
- **업무 규칙**: 확인 필요 주문의 환불은 UC-24, UC-25가 자동으로 처리하므로 운영자는 조회하고 계속 실패한 건의 사유만 확인한다. 문제 신고의 처리(환불, 반품, 분쟁 중재)는 이번 범위에 없고 표시와 조회만 한다(FR-017, FR-020). 환불 계좌번호는 마스킹해서 보여 준다.

## 자동 처리

### UC-17 만료된 재고 선점 반환

- **주 액터**: 시간 기반 처리
- **목적**: 결제가 끝나지 않은 재고 확보를 되돌려 다른 고객이 살 수 있게 한다.
- **사전 조건**: 만료 시각이 지났고 상태가 "유지"인 재고 확보가 있다.
- **사후 조건**: 재고가 더해지고 재고 확보가 반환이 되며, 주문이 취소됨이, 하위 주문이 취소가 된다.
- **기본 흐름**:
  1. 스케줄러가 1분마다 실행되어 만료된 재고 확보를 잠금과 함께 가져온다(다른 실행과 겹치지 않도록 건너뜀 방식을 쓴다).
  2. 시스템이 각 재고 확보의 상태가 "유지"인 경우에만 반환으로 바꾸고 재고를 더한다.
  3. 연결된 결제가 아직 승인 전이면(준비 또는 승인 대기, 만료 전에 대행사에 먼저 조회해 확인한 뒤) 결제를 만료로, 주문을 취소됨으로, 하위 주문을 취소로 바꾼다.
- **대안 흐름**: 서버가 여러 대여도 같은 재고 확보를 두 번 반환하지 않는다.
- **예외 흐름**:
  - 결제 결과를 알 수 없는 상태(대행사 확인 전)인 주문은 조회로 확인한 뒤에 반환한다.
  - 조회 결과 이미 승인되어 있으면 반환하지 않고 UC-04의 7d를 따라 "확인 필요"로 기록한다(UC-24가 환불).
  - 입금 대기 결제는 만료시키지 않는다. 입금 기한 기준의 만료는 UC-18이 맡는다.
- **업무 규칙**: 즉시 결제의 유지 시간은 기본 15분이며 설정으로 바꾼다. 반환은 한 번만 일어난다(SC-005). 스케줄러는 컨텍스트 저장소를 직접 부르지 않고 결제 결과 조정 서비스를 호출한다.

### UC-18 입금 기한 만료 주문 자동 취소

- **주 액터**: 시간 기반 처리
- **목적**: 입금 기한 안에 입금되지 않은 주문을 정리한다.
- **사전 조건**: 입금 대기 결제의 기한이 지났고 입금이 확인되지 않았다.
- **사후 조건**: 결제가 만료가 되고, 주문이 취소됨이, 하위 주문이 취소가 되며, 재고가 반환된다.
- **기본 흐름**:
  1. 스케줄러가 기한이 지난 입금 대기 결제를 가져온다.
  2. 시스템이 만료 처리 전에 항상 대행사에 상태를 먼저 조회해 입금되지 않았음을 확인한다.
  3. 시스템이 결제를 만료로, 주문을 취소됨으로, 하위 주문을 취소로 바꾸고 재고를 반환한다.
- **대안 흐름**: 없음.
- **예외 흐름**: 조회 결과 이미 입금되어 있으면 취소하지 않고 UC-05의 입금 처리 규칙을 따른다(기한 안 입금이면 확정, 기한 후 입금이면 "확인 필요"로 기록하고 UC-24가 환불). 만료로 취소된 뒤에 입금이 확인되어도 같다(만료 뒤 성공).
- **업무 규칙**: 입금 기한 기본값은 24시간이며 설정으로 바꾼다. 입금 기한이 지난 뒤의 입금은 자동으로 확정하지 않고 환불한다. 입금 대기 결제의 만료는 이 유즈케이스만 맡는다(UC-17은 입금 대기 결제를 만료시키지 않는다).

### UC-19 배송 완료 7일 후 자동 구매 확정

- **주 액터**: 시간 기반 처리
- **목적**: 고객이 구매 확정을 누르지 않아도 일정 기간이 지나면 확정해 정산 기준을 만든다.
- **사전 조건**: 배송 완료 시각 기준으로 정해진 기간(기본 7일)이 지났고 상태가 "배송 완료"이며 문제 신고가 없는 하위 주문이 있다.
- **사후 조건**: 하위 주문이 구매 확정이 되고 구매 확정 시각이 기록된다.
- **기본 흐름**:
  1. 스케줄러가 기간이 지난 배송 완료 하위 주문 중 문제 신고되지 않은 것을 가져온다.
  2. 시스템이 조건부로 상태를 구매 확정으로 바꾸고 시각을 기록한다.
- **대안 흐름**: 그 사이 고객이 이미 구매 확정을 눌렀다면 아무것도 하지 않는다.
- **예외 흐름**: 문제 신고된 하위 주문은 대상에서 빠지고 자동 확정되지 않는다(UC-22). 조건부 갱신으로 신고와 자동 확정이 동시에 일어나도 먼저 처리된 쪽만 반영한다.
- **업무 규칙**: 자동 확정 기간은 운영 설정으로 바꿀 수 있다. 기준은 하위 주문의 배송 완료 시각이다. 정산 기능은 구매 확정 시각을 기준으로 한다.

### UC-24 확인 필요 주문 자동 환불

- **주 액터**: 시간 기반 처리, 결제 이벤트(웹훅이나 결제 승인 확인)
- **보조 액터**: 결제 대행사
- **목적**: 주문을 확정할 수 없는데 돈이 들어온 결제를 사람의 개입 없이 전액 돌려준다.
- **사전 조건**: 주문이 "확인 필요"다(사유: 기한 후 입금, 재고 확보 만료 뒤 결제 성공, 금액 불일치). 재고 확보 만료나 입금 기한 만료로 취소된 주문에 뒤늦게 승인이나 입금이 확인된 경우도 포함한다.
- **사후 조건**: 결제 금액 전액의 환불이 완료되고 주문이 "환불됨"이 된다. 환불은 정확히 한 번만 이루어진다(SC-010).
- **기본 흐름**:
  1. 결제 결과 처리(UC-04의 7d, UC-05의 5a·5b, UC-17, UC-18)가 주문을 "확인 필요"로 바꿀 때, 같은 트랜잭션에서 사유를 기록하고 환불(대상: 주문 전체, 금액: 결제 금액, 사유: 확인 필요 환불)을 "요청"으로 기록한다.
  2. 시스템이 대행사에 전액 환불을 요청한다. 가상계좌 결제는 결제 시작 때 받은 환불 계좌를 쓴다.
  3. 환불이 성공하면 환불을 완료로 바꾸고, 환불 거래 내역을 추가하고, 주문을 "환불됨"으로 바꾸고, 환불 계좌번호를 가린다.
- **대안 흐름**: 서버가 1단계 직후 멈추면 UC-25가 "요청" 상태의 환불을 찾아 이어 간다. 스케줄러가 환불이 아직 없는 확인 필요 주문을 발견하면 환불을 새로 기록한다.
- **예외 흐름**:
  - 2a. 대행사 환불이 실패하거나 결과를 알 수 없으면 환불을 "실패" 또는 "확인 중"으로 기록하고 UC-25가 이어 간다. 주문은 "확인 필요"로 남는다.
  - 같은 결제에 환불이 이미 완료되었거나 진행 중이면 새로 만들지 않는다(이중 환불 방지).
  - 조회 결과 이미 환불된 것으로 확인되면 대행사를 다시 부르지 않고 완료로 기록한다.
- **업무 규칙**: 확인 필요 주문은 확정하지 않는다. 환불 계좌번호는 암호화해 저장하고 기록에 남기지 않는다(FR-015). 운영자는 UC-16에서 진행을 조회한다.

### UC-25 환불 재시도와 결과 확인

- **주 액터**: 시간 기반 처리
- **보조 액터**: 결제 대행사
- **목적**: 끝나지 않았거나 실패한 환불(고객 취소, 판매자 취소, 확인 필요 환불, 결제 대기 취소)을 끝까지 이어 간다.
- **사전 조건**: 상태가 "요청", "확인 중", "실패"인 환불이 있고 재시도 간격(설정값)이 지났다.
- **사후 조건**: 환불이 완료되거나, 재시도 한도(설정값)를 넘겨 운영자 확인 대상이 된다.
- **기본 흐름**:
  1. 스케줄러가 대상 환불을 잠금과 함께 가져온다(다른 실행과 겹치지 않도록 건너뜀 방식을 쓴다).
  2. "확인 중"이나 "요청"이면 시스템이 대행사에 환불 결과를 먼저 조회한다. 이미 완료되었으면 완료로 기록한다.
  3. 대행사에 환불이 없으면 "실패" 환불은 새 요청(새 중복 방지 식별값)으로 이어 가고, "요청" 환불은 그대로 대행사에 요청한다.
  4. 성공하면 환불을 완료로 바꾸고 환불 거래 내역을 추가한다. 확인 필요 환불이면 주문을 "환불됨"으로 바꾼다.
- **대안 흐름**: 서버가 여러 대여도 같은 환불을 두 번 처리하지 않는다.
- **예외 흐름**: 재시도 한도를 넘겨 계속 실패하면 "실패"로 남기고 운영자가 UC-16에서 사유를 확인한다. 하위 주문별 환불 합계가 하위 주문 금액을 넘는 요청은 만들지 않는다.
- **업무 규칙**: 재시도 간격과 횟수는 설정값이며 계획 단계에서 정한다. 이미 끝난 취소와 재고 반환은 환불 재시도로 되돌리지 않는다. 스케줄러는 결제 결과 조정 서비스를 호출한다.
