# 설계 검토 결과: 멀티 판매자 이커머스 핵심 구매·판매 흐름

**관련 이슈**: #3

**검토일**: 2026-10-12

**검토 대상**: spec.md, plan.md, data-model.md, usecase-details.md, tasks.md, traceability.md, schema.sql, contracts/

**검토 방식**: 설계자, 개발자, 고객, 판매자 네 페르소나를 서브에이전트로 병렬 실행해 **비판적 시각**으로만 검토했다. 칭찬과 장점은 일부러 뺐다.

**확인 수준 표기**
- **직접 확인**: 검토를 정리한 쪽이 문서를 직접 읽거나 검색해 확인했다.
- **지적**: 에이전트가 지적했고 개별 대조는 하지 않았다. 반영 전에 확인이 필요하다.

---

## 1. 총평

- 설계의 뼈대(재고 선점, 멱등키, 판매자별 하위 주문)는 문서 전반에서 일관된다.
- 약점은 **정상 경로 밖**에 몰려 있다. 결제 만료 뒤 성공 도착, 환불 실패, 판매자·고객이 막다른 길에 놓이는 경우다. 이 구간은 상태 전이표가 서로 어긋나거나 "이번 범위 밖"으로 처리돼 있다.
- 작업 계획(tasks.md)은 "테스트 먼저"와 "스토리 독립" 두 원칙을 구조적으로 지키기 어렵다.
- 추적 매트릭스(traceability.md)에는 허위 연결 2건과 누락 연결이 있다. 요구사항에 없는 빈틈은 매트릭스가 구조적으로 잡지 못한다.

|---|------|--------|------|

| R-05 | `환불 대기` 상태가 데이터 모델에 없다. 환불 재시도 작업과 환불 유일 제약도 없고, 합계 상한 검사는 애플리케이션에만 있다. | 높음 | 직접 확인 |
| R-06 | 웹훅이 처리 실패에도 200을 주면 대행사가 재전송하지 않아 입금이 유실된다. 처리 실패는 5xx로 응답해야 한다. | 높음 | 지적 |

| R-09 | 입금 대기 24시간 선점을 악용할 수 있다. 고객당 동시 미결제 주문·수량 상한이 없다. | 높음 | 직접 확인 |
| R-10 | `준비→만료` 전이가 없다. UC-17과 UC-18이 입금 대기 만료를 서로 다른 기준으로 처리한다. 주문당 비종료 결제 하나를 강제하는 제약이 없다. | 높음 | 지적 |
| R-11 | 확인 필요 진입 시 재고 확보와 하위 주문의 상태가 정의돼 있지 않고, 사유 열이 없다(UC-16은 사유 조회를 요구). | 높음 | 직접 확인(사유 열 없음) |

## 3. 사람이 막다른 길에 놓이는 문제 (고객, 판매자)

| # | 문제 | 심각도 | 확인 |
|---|------|--------|------|
| P-01 | 판매자 거절은 영구 배제다. 종료 상태이고 사업자번호가 유일하며 재신청이 막혀 있고, 거절 사유 필드와 서류 보완 수단이 없다. | 치명 | 직접 확인(사유 필드 없음) |
| P-02 | 판매자가 주문을 취소하거나 품절 처리할 수 없고, 발송 기한이 없다. 취소 주체가 고객뿐이다. | 치명 | 지적 |
| P-03 | 현금흐름이 불명확하다. 배송 중→배송 완료 자동 전이가 없어, 판매자가 누르지 않으면 정산 기준 시각이 생기지 않는다. 정산 주기와 지급일 정의도 없다. | 치명 | 지적 |
| P-04 | 송장과 배송 완료 오입력을 고칠 수 없다. 배송 완료는 되돌릴 수 없고 7일 뒤 자동 확정된다. | 높음 | 지적(되돌리기 거절은 spec US4-5로 확인) |
| P-05 | 고객은 결제 대기 주문을 취소하거나 결제수단을 바꿀 수 없다. 자기 선점 때문에 스스로 재고 부족을 겪는다. | 높음 | 직접 확인 |
| P-06 | 분쟁 수단 없이 7일 뒤 자동 확정된다. 판매자가 단독으로 "배송 완료"를 찍으면 미수령, 불량, 오배송 구제 경로가 없다. | 높음 | 지적 |
| P-07 | 정지 판매자의 진행 중 주문이 방치된다. 사전 조건이 "승인된 판매자"라 발송도 막혀 보인다. | 높음 | 직접 확인(결정 미정) |
| P-08 | 소비자 보호 요소가 없다(판매자 정보 표시, 약관·개인정보 동의, 청약철회). **법률 검토 필요.** | 높음 | 지적 |
| P-09 | 재고 수정 입력이 총량인지 증감인지 정의돼 있지 않아, 선점 반환과 동시에 수정하면 충돌한다. | 높음 | 직접 확인 |
| P-10 | 계정 복구(비밀번호 재설정)와 탈퇴가 없다. | 중간 | 지적 |
| P-11 | 알림이 없다. 입금 계좌 안내는 결제 직후 1회뿐이라 다시 볼 수 없고, 신규 주문·재고 부족·신청 상태도 알 수 없다. | 중간 | 지적 |
| P-12 | 탐색이 이름 검색과 판매자별 보기뿐이다. 카테고리와 정렬이 없어 상품 1만 개에서 SC-002가 위험하다. | 중간 | 지적 |
| P-13 | 담기에 로그인이 필요한데 로그인 후 원래 상품으로 복귀하는 규정이 없다. 오류 시 입력값 보존 규정도 없다. | 중간 | 지적 |
| P-14 | 하위 주문 항목에 상품명·옵션명 스냅샷이 없다. 옵션을 바꾸거나 지우면 과거 주문 표시가 깨진다. | 중간 | 지적 |
| P-15 | 판매자에게 보이는 배송지의 마스킹·보관 규칙이 없다. 취소된 하위 주문이 FR-011a의 비노출 대상이 아니다. | 중간 | 지적 |
| P-16 | 사진·옵션 개수 한도와 일괄 입력이 없다. 옵션 10×10이면 조합 100개를 하나씩 입력해야 해 SC-001과 충돌한다. | 중간 | 지적 |
| P-17 | 판매 실적 조회, 입점 후 정보 수정, 자진 탈퇴, 신청 상태 화면과 심사 기한이 없다. | 낮음 | 지적 |
| P-18 | 포장·택배 접수 뒤 고객이 취소하면 송장 입력이 거절된다. "발송 준비 중" 상태가 없다. | 낮음 | 지적 |

| W-05 | 결정 항목 순서가 거꾸로다. T127(재고 확보 상태)은 열거형이 V1에 들어간 뒤, T148(정지 판매자)은 T044 구현 뒤, T149(재신청)는 T033 시험 작성 뒤에 결정된다. | 높음 |

| W-07 | 필수 작업과 필드가 빠져 있다. 운영자 계정 시드, 엔티티의 `public_id`, T091의 `stock_id`, 로그인 계정과 `seller_id` 매핑, 결제 시작 시 고객이 확인한 금액 입력 계약. | 높음 |
| W-08 | 정의되지 않은 값이 많다. 페이지 크기와 정렬, 파일 크기·형식 수치, 대행사 타임아웃과 재시도·재조회 주기, 멱등키 TTL, 입금 기한과 `expires_at`의 출처, 멱등키를 폼 값으로 받을지 헤더로 받을지. | 높음 |

| W-10 | 사람 시간 기준 SC(SC-001, SC-002, SC-007, SC-008)는 자동 테스트로 잴 수 없다. T115는 동기 DB 읽기라 시험 의미가 없다. 수동 확인 작업으로 분리해야 한다. | 중간 |
| W-11 | 환불 합계 상한 검사에 DB 보호(부분 유일 인덱스나 잠금)가 없다. | 중간 |

## 7. 권장 순서

1. **결제·환불 상태머신을 하나로 확정한다(2절 전부).**
   - 결제, 주문, 재고 확보의 전이표를 하나로 맞춘다. 만료 후 성공, 취소됨→확인 필요, 준비→만료, 확정→취소됨을 포함한다.
   - 환불 대기 상태, 환불 재시도, 환불 유일 제약, 가상계좌 환불계좌 수집을 정한다.
   - 웹훅 처리 실패는 5xx로 응답하고 GET 상태 변경은 없앤다.
   - 결제 대기 주문의 하위 주문 취소를 막는다.
   - 멱등키 `처리 중`에 회수 규칙을 둔다.
   - 고객이 확인한 금액을 `POST /checkout`에서 받아 서버 계산값과 대조한다.
2. **범위 결정 6건을 구현 전에 정한다.** 사용자 판단이 필요하다.
   - 확인 필요 주문의 자동 전액 환불을 이번 범위에 넣을지
   - 판매자 직접 취소와 발송 기한을 넣을지
   - 거절 후 재신청과 서류 보완을 허용할지
   - 분쟁 보류 상태를 최소한으로 넣을지
   - 정지 판매자의 진행 중 주문을 어떻게 처리할지
   - 결제 대기 주문의 고객 취소와 결제수단 변경을 넣을지
3. **헌법 정합성을 정리하고 ADR을 가져온다.** 헌법 개정(T151)을 구현 선행 조건으로 올리고, 복잡성 표에 헌법 IX 이탈과 사유를 적는다. ADR(PR #5)을 먼저 머지하거나 이 브랜치로 가져온다.
4. **tasks.md를 재정렬하고 누락 작업을 추가한다(5절).** US2를 US1 뒤로 직렬화하고, 기반 테스트를 해당 엔드포인트가 생기는 스토리로 옮기며, 결제 결과 조정 작업과 판매자 상태 조회 인터페이스 작업을 추가한다.
5. **추적 매트릭스를 고친다(6절).** 오류를 정정하고 G-9 이후 빈틈을 추가한다. 가능하면 tasks.md와 매트릭스의 불일치를 자동으로 검사하는 스크립트를 둔다.

## 8. 이 검토의 한계

- 에이전트 지적 중 "지적"으로 표시한 항목은 개별 대조를 하지 않았다. 반영 전에 해당 문서의 근거를 확인해야 한다.
- 가상계좌 환불계좌(R-02)는 결제 대행사 사양 확인이 필요하다.
- 소비자 보호(P-08)와 개인정보(P-15) 항목은 법률 검토가 필요하며, 이 문서는 법적 결론을 내리지 않는다.
- 판매자 에이전트의 "재고 100개로 입력해도 팔린 30개가 반영되지 않아 과판매"라는 서술은 확정된 결함이 아니라, 입력값의 의미가 정의돼 있지 않다는 문제(P-09)의 한 가지 해석이다.
- 비판적 검토만 수행했으므로 설계의 장점과 이미 잘 처리된 부분은 이 문서에 없다.
