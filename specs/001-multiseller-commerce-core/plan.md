# 구현 계획: 멀티 판매자 이커머스 핵심 구매·판매 흐름

**브랜치**: `feature/3-multiseller-commerce-core` | **작성일**: 2026-10-08 | **명세**: [spec.md](spec.md)

**관련 이슈**: #3

**입력**: [spec.md](spec.md)의 기능 명세

## 요약

여러 판매자가 입점하는 쇼핑몰의 핵심 구매·판매 흐름을 만든다. 판매자 입점과 상품(옵션) 등록, 고객의 탐색과 장바구니, 재고 선점 후 멱등 결제(즉시 결제와 입금 대기), 판매자별 하위 주문의 배송과 구매 확정, 발송 전 취소와 전액 환불까지 다룬다. 정산은 제외하되 구매 확정 시각을 기록해 둔다.

기술 접근: 스프링 부트 단일 애플리케이션을 기능 단위 패키지로 나누는 모듈형 모놀리스로 만든다. 재고 차감은 조건부 갱신 쿼리로 원자적으로 처리하고, 멱등키는 유일 제약이 있는 테이블에 기록한다. 결제는 외부 결제 대행사를 포트(인터페이스) 뒤에 두어 테스트에서는 가짜 구현으로 바꾼다.

## 기술 맥락

**언어/버전**: 자바 21, 스프링 부트 3.x

**주요 의존성**: 스프링 MVC, 타임리프, 스프링 시큐리티, 스프링 데이터 JPA, 스프링 데이터 REST, 플라이웨이(마이그레이션), 밸리데이션

**저장소**: 포스트그레스큐엘 (운영과 테스트 모두 같은 종류 사용)

**테스트**: 제이유닛 5, AssertJ, 스프링 부트 테스트(`@WebMvcTest`, `@DataJpaTest`, `@SpringBootTest`), 스프링 시큐리티 테스트, 테스트컨테이너스(포스트그레스큐엘)

**빌드 도구**: 그레이들

**결제 대행사**: 토스페이먼츠 (카드 즉시 결제, 가상계좌 입금 대기, 웹훅, 멱등키 지원). 포트 뒤에 두어 교체 가능하게 한다.

**대상 플랫폼**: 리눅스 서버, 웹 브라우저 이용

**프로젝트 유형**: 서버 렌더링 웹 애플리케이션 (단일 프로젝트). 화면 MVC 계층과 REST API 계층을 나눈다(ADR-0008).

**성능 목표**: 상품 목록·상세 응답 p95 1초 이내, 결제 시작 요청 p95 2초 이내 (결제 대행사 응답 제외)

**제약**: 재고 1개에 동시 주문 100건이 몰려도 정확히 1건만 성공, 같은 결제·취소 요청은 몇 번 와도 한 번만 처리

**규모/범위**: 초기 동시 사용자 500명, 판매자 100곳, 상품 10,000개 수준. 단일 서버 한 대 기준으로 설계하고 예약 작업은 데이터베이스 잠금으로 중복 실행을 막는다.

**구조 결정**: 단일 그레이들 프로젝트에 기능 단위 패키지를 둔다. 패키지는 바운디드 컨텍스트와 같고(계정, 상품, 주문, 재고, 결제, 배송, 공통), 각 컨텍스트가 맡는 개체는 [data-model.md](data-model.md)와 [클래스 다이어그램](diagrams/data-model-class.png)에 있다. 패키지 사이 호출은 서비스 인터페이스로만 하고, 다른 패키지의 저장소를 직접 쓰지 않는다. 나중에 분리해야 할 때 경계가 이미 나뉘어 있도록 하기 위함이다.

**계층 구조**: 전통적인 MVC 하나로 만들지 않고 네 층으로 나눈다([ADR-0008](../../docs/adr/0008-layered-rest-repository.md), [컴포넌트 다이어그램](diagrams/c4-component.png)).

1. **화면 MVC 계층(프론트엔드 제어)**: 스프링 MVC와 타임리프. 화면 흐름과 폼 처리, 화면 모델 만들기만 맡는다. 업무 서비스나 리포지토리를 직접 부르지 않고 API 클라이언트만 쓴다. 프론트엔드를 분리할 때 이 계층이 프론트엔드로 옮겨 간다.
2. **REST API 계층**: 컨텍스트마다 스프링 데이터 REST로 읽기용 리소스를 노출하고, 상태를 바꾸는 일은 동작 컨트롤러가 맡는다. 재고와 배송은 REST로 노출하지 않는다.
3. **서비스 계층**: 업무 규칙(상태 전이, 조건부 갱신, 멱등, 컨텍스트 사이 조정).
4. **리포지토리 계층**: 스프링 데이터 JPA. 상태 변경은 조건부 갱신 질의로만 한다.

스프링 데이터 REST 사용 규칙: 상태를 가진 개체(재고, 결제, 하위 주문 상태, 멱등키, 변경 이력)는 쓰기용 리소스로 노출하지 않는다. 상태 전이, 결제 시작, 취소, 발송 처리는 동작 컨트롤러가 서비스를 거쳐서만 한다. 읽기 리소스는 리포지토리의 권한 조건으로 본인 것만(판매자는 확정된 주문의 하위 주문만) 돌려준다. REST API 계약은 구현 전에 `contracts/`에 따로 정리한다(아직 없음).

**배포 구조 방향**: 목표는 컨텍스트마다 별도 인스턴스로 배포하고, 프론트엔드도 나중에 별도 인스턴스로 분리하는 것이다. 첫 구현은 분리 가능한 모듈형 모놀리스로 시작한다([ADR-0007](../../docs/adr/0007-context-deployment-strategy.md)). 그래서 첫 구현부터 아래 규칙을 지킨다.

- 컨텍스트 사이 참조는 식별자 값으로만 한다. 데이터베이스 외래키와 조인을 컨텍스트 사이에 쓰지 않는다.
- 컨텍스트마다 자기 테이블만 읽고 쓴다. 다른 컨텍스트의 데이터는 서비스 인터페이스로만 얻는다.
- 컨텍스트를 가로지르는 흐름(결제 시작, 결제 성공, 발송 전 취소)은 한 곳의 조정 서비스가 맡고, 각 단계를 멱등하게 만들어 나중에 보상 처리로 바꿀 수 있게 한다.
- 컨텍스트마다 자기 마이그레이션 폴더와 멱등키 사용 범위를 가진다.
- 화면(타임리프)은 서비스 인터페이스만 호출하고 도메인 객체를 직접 다루지 않는다. 프론트엔드를 분리할 때 호출 대상만 바뀌게 하기 위함이다.
- 프론트엔드를 단일 페이지 앱으로 분리하는 경우에는 헌법의 기술 스택 섹션에 따라 근거를 문서로 남기고, 서버 렌더링을 유지한 채 별도 인스턴스로 분리하는 경우에는 그대로 따른다.

## 복잡성 추적

첫 구현은 헌법 위반이 없어 비워 둔다. 컨텍스트를 별도 인스턴스로 나누는 시점에는 분산 정합성(보상 처리, 메시지 전달) 도입에 대한 정당화를 이 표에 적고 ADR을 새로 쓴다.
