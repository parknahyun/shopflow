# 데이터 모델: 멀티 판매자 이커머스 핵심 구매·판매 흐름

모든 금액은 원 단위 정수다. 모든 테이블은 생성 시각과 수정 시각을 가진다. 화면과 외부에 노출되는 식별자는 별도의 공개용 식별자를 쓴다.

이 문서는 [ADR-0009](../../docs/adr/0009-review-decisions-payment-refund-scope.md)의 결정을 따른다.

## 바운디드 컨텍스트

개체는 일곱 개의 컨텍스트로 나눈다. 컨텍스트는 소스 코드의 기능 단위 패키지와 같다([plan.md](plan.md)의 프로젝트 구조). 그림은 [diagrams/data-model-class.png](diagrams/data-model-class.png)에 있다.

| 컨텍스트 | 맡는 개체 | 맡는 일 |
|----------|-----------|---------|
| 계정 | 계정, 판매자 정보, 입점 서류 | 가입, 로그인, 입점 신청·승인·거절(사유 기록)·재신청, 사업자 정보와 서류 보관 |
| 상품 | 상품, 판매 단위 | 상품과 옵션 조합 등록, 검색 |
| 주문 | 장바구니 항목, 주문, 하위 주문, 하위 주문 항목 | 장바구니, 주문 생성, 하위 주문 상태 전이, 고객·판매자 취소, 결제 대기 주문 취소, 문제 신고 표시, 구매 확정 |
| 재고 | 재고, 재고 확보 | 판매 단위별 총 보유 수량과 가용 수량 소유, 재고 선점, 확정, 반환, 만료 처리 |
| 결제 | 결제, 결제 거래 내역, 환불, 환불 계좌 | 결제 승인, 입금 확인, 환불 요청·재시도, 대행사 연동 |
| 배송 | 배송 정보 | 송장 입력, 배송 완료 시각 기록 |
| 공통 | 멱등키, 감사 이력 | 여러 컨텍스트가 함께 쓰는 중복 방지와 변경 이력 |

- 컨텍스트 사이의 호출은 서비스 인터페이스로만 하고, 다른 컨텍스트의 저장소는 직접 쓰지 않는다.
- **컨텍스트 사이 참조는 식별자 값으로만 한다.** 다른 컨텍스트 개체를 가리킬 때 데이터베이스 외래키와 조인을 쓰지 않는다. 컨텍스트를 별도 인스턴스로 나눌 수 있게 하려는 규칙이다([ADR-0007](../../docs/adr/0007-context-deployment-strategy.md)). 아래 개체 설명에서 컨텍스트를 넘는 "참조"는 식별자 참조를 뜻한다.
- 비동기 결제 결과(웹훅, 승인 확인, 만료 작업, 환불 재시도)는 컨텍스트를 가로지르는 조정 서비스 `PaymentResultCoordinator`가 지휘한다. 스케줄러는 컨텍스트 저장소를 직접 부르지 않고 이 조정 서비스를 호출한다(ADR-0009 결정 C).
- 판매 단위별 가용 재고 수량은 **재고 컨텍스트의 `재고` 개체가 소유**한다. 상품 컨텍스트의 판매 단위는 재고 수량을 갖지 않는다. 판매자가 상품을 등록하거나 재고를 고치면 상품 컨텍스트가 재고 컨텍스트의 서비스를 호출한다.
- 하위 주문의 배송 상태 전이(취소와 발송이 동시에 올 때 먼저 처리된 요청만 반영하는 규칙 포함)는 주문 컨텍스트가 상태 한 곳에서 조건부로 처리한다. 배송 컨텍스트는 송장과 배송 완료 시각만 맡는다. 자동 구매 확정이 배송 완료 시각을 기준으로 하므로 하위 주문이 배송 완료 시각을 복사해 가진다.

## 개체와 관계

다중도는 `1`(정확히 하나), `0..1`(없거나 하나), `0..*`(0개 이상), `1..*`(1개 이상)로 쓴다. 속성은 값이 없을 수 있으면 "(선택)"이라고 적고, 적지 않은 속성은 필수다.

```text
계정(고객) 1 ─ 0..* 장바구니 항목 0..* ─ 1 판매 단위 1..* ─ 1 상품 0..* ─ 1 판매자 정보
계정(고객) 1 ─ 0..* 주문 1 ─ 1..* 하위 주문 0..* ─ 1 판매자 정보
하위 주문 1 ─ 1..* 하위 주문 항목 0..* ─ 1 판매 단위
하위 주문 1 ─ 0..1 배송 정보                       (송장을 입력하면 생긴다)
주문 1 ─ 0..* 결제 1 ─ 1..* 결제 거래 내역
결제 거래 내역 0..* ─ 0..1 하위 주문               (환불일 때만 대상이 있다)
결제 1 ─ 0..* 환불 0..* ─ 0..1 하위 주문           (하위 주문 환불이면 대상이 있고, 주문 전체 환불이면 없다)
환불 1 ─ 0..* 결제 거래 내역                       (환불이 완료되면 환불 행이 추가된다)
결제 1 ─ 0..1 환불 계좌                            (입금 대기 방식 결제만)
주문 1 ─ 0..* 재고 확보 0..* ─ 1 판매 단위
판매 단위 1 ─ 1 재고 1 ─ 0..* 재고 확보
계정 1 ─ 0..1 판매자 정보 1 ─ 1..* 입점 서류       (판매자 계정만 판매자 정보가 있다)
```

위의 `1..*` 같은 최소 1 규칙은 업무 규칙이다. 데이터베이스는 자식이 0개인 상태를 막지 못하므로 애플리케이션이 지킨다. DB ERD([schema-erd-ie.png](diagrams/schema-erd-ie.png))에는 데이터베이스가 지키는 규칙(외래키 컬럼의 NULL 허용 여부, 유일 제약)만 표시한다.

## 개체

### 계정 (고객, 판매자, 운영자)
- 유형(고객, 판매자, 운영자), 이메일, 비밀번호 해시, 상태
- 규칙: (유형, 이메일)이 유일하다. 비밀번호는 솔트가 적용된 해시만 저장한다. 고객 계정은 판매 기능을, 판매자 계정은 장바구니와 주문 기능을 쓸 수 없다.

### 판매자 정보
- 계정 참조, 사업자 유형(개인사업자, 법인사업자), 상호명, 사업자등록번호, 대표자명, 연락처, 사업장 주소, 통신판매업 신고번호, 법인명(선택, 법인만), 법인등록번호(선택, 법인만), 입점 상태(신청, 승인, 거절, 정지), 거절 사유(선택, 거절일 때 필수)
- 상태 전이: 신청 → 승인 또는 거절, 승인 → 정지, 정지 → 승인, **거절 → 신청**(재신청). 거절은 더 이상 종료 상태가 아니다.
- 규칙: 사업자등록번호는 유일하다. 법인사업자는 법인명과 법인등록번호가 필수이고 개인사업자는 비어 있어야 한다. 대표자 주민등록번호는 저장하지 않는다. 승인 상태가 아니면 상품을 등록할 수 없고, 정지·거절 판매자의 상품은 고객에게 보이지 않는다. 사업자 등록이 없는 개인은 입점할 수 없다.
- 운영자는 거절할 때 거절 사유를 반드시 적는다. 판매자는 승인 전이라도 로그인해 자기 입점 상태와 거절 사유를 조회할 수 있다.
- 거절된 판매자는 같은 계정, 같은 판매자 정보 행을 고쳐서 다시 신청한다(거절 → 신청). 행을 새로 만들지 않으므로 사업자등록번호 유일 제약과 충돌하지 않는다.
- 정지는 **신규 판매만 막는다.** 정지된 판매자의 상품은 고객에게 보이지 않고 새 상품을 등록할 수 없다. 이미 확정된 주문(진행 중 주문)의 하위 주문은 발송 처리, 배송 완료 처리, 판매자 취소를 계속할 수 있다.

### 입점 서류
- 판매자 정보 참조, 서류 종류(사업자등록증 사본 등), 파일 저장 위치, 제출 시각
- 규칙: 판매자 정보를 만들 때 함께 제출되고, 신청·거절 상태에서는 다시 올릴 수 있다(재신청 때 서류를 보완한다). 판매자 본인과 운영자만 조회할 수 있다. 파일은 서버가 정한 이름으로 비공개 위치에 저장하고 허용 형식과 크기를 검사한다. 국세청 진위 확인과 정산 계좌는 이번 범위에서 제외한다.

### 상품
- 판매자 참조, 이름, 설명(선택), 사진 목록, 판매 상태(판매 중, 판매 중지)
- 규칙: 하나 이상의 판매 단위를 가진다. 이름은 비어 있을 수 없다.

### 판매 단위 (옵션 조합)
- 상품 참조, 옵션 값 목록(예: 색상=빨강, 사이즈=M), 가격
- 규칙: 가격은 0보다 크다. 한 상품 안에서 옵션 값 조합은 유일하다. 옵션이 없는 상품은 판매 단위가 하나다. 재고 수량은 [재고](#재고) 개체가 소유한다.

### 장바구니 항목
- 고객 참조, 판매 단위 참조, 수량
- 규칙: (고객, 판매 단위)가 유일하다. 수량은 1 이상이다. 재고보다 많은 수량으로는 주문을 시작할 수 없다. 한 주문에서 판매 단위별 수량은 상한(기본 10개, 설정값)을 넘을 수 없다.

### 주문
- 고객 참조, 총 금액, 상태(결제 대기, 확정, 취소됨, 확인 필요, 환불됨), 확인 필요 사유(선택, 확인 필요일 때 필수), 배송지 정보
- 총 금액은 **주문 생성 시점의 하위 주문 금액 합계**이며 이후 일부 취소로 바뀌지 않는다. 남은 금액은 취소되지 않은 하위 주문 금액으로 계산한다.
- 확인 필요 사유: 기한 후 입금, 재고 확보 만료 뒤 결제 성공, 금액 불일치. 운영자가 목록에서 사유를 조회한다(UC-16).
- 상태 전이 (허용 목록):

| 현재 상태 | 이동 가능한 상태 | 조건 |
|-----------|------------------|------|
| 결제 대기 | 확정 | 결제 성공 확인(서버가 대행사에 조회) |
| 결제 대기 | 취소됨 | 결제 실패, 시간 초과, 입금 기한 만료, 고객 직접 취소 |
| 결제 대기 | 확인 필요 | 재고 확보 만료 뒤 결제 성공, 금액 불일치 |
| 취소됨 | 확인 필요 | 결제 만료로 취소된 뒤(고객 직접 취소 포함) 승인이나 입금이 서버 조회로 확인됨(만료 뒤 성공) |
| 확정 | 취소됨 | 모든 하위 주문이 취소됨 |
| 확인 필요 | 환불됨 | 자동 전액 환불 완료 |
| 환불됨 | (없음) | 종료 |
| 취소됨(확정 이후에 취소된 것) | (없음) | 종료 |

- 규칙: 확정 이후에는 하위 주문 상태가 모두 취소이면 주문도 취소됨으로 본다. 주문이 결제 대기에서 취소됨으로 바뀌면 속한 하위 주문도 모두 취소로 바꾼다(같은 트랜잭션).
- **확인 필요가 될 때** 같은 트랜잭션에서 아직 취소되지 않은 하위 주문을 취소(주체 시스템, 사유 "확인 필요")로 바꾸고, 재고 확보가 유지 상태이면 반환으로 바꾸며 재고를 더한다. 이미 반환된 재고는 다시 차감하지 않는다. 확인 필요 주문은 판매자에게 보이지 않는다.
- 확인 필요 주문은 결제 금액을 **자동으로 전액 환불**한다. 환불이 완료되면 주문은 환불됨이 된다. 환불이 계속 실패하면 주문은 확인 필요로 남고 운영자가 실패 사유를 확인한다.
- 결제 대기 주문은 **고객이 주문 단위로 취소**할 수 있다. 결제수단 변경은 취소 후 다시 주문하는 것으로 대신한다. 결제 대기 주문의 하위 주문 하나만 따로 취소할 수는 없다.
- 고객당 **동시 결제 대기 주문 수**는 상한(기본 3건, 설정값)을 넘을 수 없다. 넘으면 결제를 시작하지 않고 기존 결제 대기 주문을 먼저 취소하라고 안내한다.

### 하위 주문
- 주문 참조, 판매자 참조, 금액, 배송 상태, 구매 확정 시각(선택), 취소 시각(선택), 취소 주체(선택, 고객·판매자·시스템), 취소 사유(선택, 판매자 취소는 필수), 배송 완료 시각(선택, 복사값), 문제 신고 시각(선택), 문제 신고 사유(선택) (송장 정보는 [배송 정보](#배송-정보)가 맡는다)
- 배송 상태 전이 (허용 목록):

| 현재 상태 | 이동 가능한 상태 |
|-----------|------------------|
| 발송 전 | 배송 중, 취소 |
| 배송 중 | 배송 완료 |
| 배송 완료 | 구매 확정 |
| 구매 확정 | (없음) |
| 취소 | (없음) |

- 하위 주문은 결제를 시작할 때 주문(결제 대기)과 함께 만든다(FR-011). 결제가 실패하거나 만료되거나 고객이 결제 대기 주문을 취소하면 주문과 함께 취소로 바뀌고, 이때는 환불할 결제가 없다.
- **취소는 속한 주문이 확정된 뒤에만** 할 수 있다. 결제 대기 주문의 하위 주문 단독 취소는 거절한다(재고 이중 반환을 막는다. 결제 대기 주문에는 주문 단위 취소만 있다).
- 취소 주체와 사유를 기록한다. 고객 취소는 사유가 선택이고 **판매자 취소는 사유가 필수**다. 시스템 취소(결제 실패, 만료, 확인 필요)는 사유에 원인을 적는다.
- 판매자는 자기 하위 주문 중 **속한 주문이 확정된 것만** 조회하고 바꿀 수 있다(FR-011a). 정지된 판매자도 이미 확정된 자기 하위 주문의 발송, 배송 완료, 취소는 할 수 있다.
- 취소는 고객과 판매자 모두 발송 전에서만 할 수 있고 흐름이 같다. 상태를 취소로 바꾸는 조건부 갱신, 재고 가산(한 번만), 환불 행 기록(상태 "요청")을 **한 트랜잭션**에서 하고, 그 뒤에 대행사 환불을 호출한다. 환불 금액은 하위 주문 금액 전액이다.
- 배송 중과 취소는 서로 배타적이며 상태 변경은 `WHERE 상태 = 현재 상태` 조건부 갱신으로 먼저 처리된 요청만 반영한다.
- 판매자의 발송 기한 초과 자동 취소는 이번 범위에 없다. 발송 지연은 판매자 화면에 표시만 하고 상태는 바꾸지 않는다.
- **문제 신고**: 고객은 배송 완료 상태이고 구매 확정 전인 하위 주문에 사유(필수)를 적어 문제를 신고할 수 있다. 신고하면 문제 신고 시각과 사유를 기록하고, 신고된 하위 주문은 자동 구매 확정 대상에서 빠지며 운영자가 조회한다. 배송 상태 전이는 바뀌지 않는다. 신고 처리(환불, 반품, 분쟁 중재)는 다음 기능에서 다루며 이번 범위는 표시와 조회뿐이다.
- **자동 구매 확정**은 배송 완료 시각을 기준으로 7일(설정값)이 지난 하위 주문에 한다. 하위 주문은 배송 완료 처리 때 [배송 정보](#배송-정보)의 배송 완료 시각을 같은 값으로 복사해 가진다. `updated_at`은 기준으로 쓰지 않는다.

### 배송 정보
- 하위 주문 참조, 택배사, 송장 번호, 배송 완료 시각(선택)
- 규칙: 판매자가 송장을 입력할 때 만들어지고, 하위 주문 하나에 최대 하나다(유일 제약). 송장 입력과 하위 주문의 배송 상태 변경("발송 전" → "배송 중")은 같은 트랜잭션에서 처리하며, 하위 주문이 이미 취소되었으면 송장을 저장하지 않는다. 배송 완료 시각은 판매자가 배송 완료 처리를 할 때 기록하며, 같은 값을 하위 주문이 복사해 가진다(자동 구매 확정 기준). 정지된 판매자도 이미 확정된 주문의 송장 입력과 배송 완료 처리는 할 수 있다.

### 하위 주문 항목
- 하위 주문 참조, 판매 단위 참조, 수량, 주문 당시 단가
- 규칙: 주문 당시 단가를 복사해 두어 이후 가격이 바뀌어도 주문 금액이 달라지지 않는다.

### 재고
- 판매 단위 식별자(참조), 총 보유 수량, 가용 수량, 버전
- 규칙: 판매 단위마다 하나다(유일 제약). 가용 수량은 0 이상이며 데이터베이스 제약으로 음수를 막는다. 값은 재고 컨텍스트가 조건부 갱신으로만 바꾼다.
- 판매자의 재고 수정은 **총 보유 수량을 입력**하는 방식이다. 가용 수량 = 총 보유 수량 − 선점되어 묶인 수량(재고 확보 유지) − 판매된 수량이며 서버가 계산해 반영한다. 구현은 `새 가용 수량 = 현재 가용 수량 + (입력한 총 보유 수량 − 기존 총 보유 수량)`을 **버전 검사가 붙은 조건부 갱신**으로 한다. 계산 결과가 음수가 되는 입력은 거절하고, 버전이 달라졌으면(동시 수정, 동시에 일어난 선점·반환) 다시 읽어 확인하게 한다.
- 총 보유 수량은 판매자가 입력할 때만 바뀐다. 선점, 확정, 반환, 취소 가산은 가용 수량만 바꾸므로 총 보유 수량 = 가용 수량 + 유지 수량 + 판매된 수량이 항상 성립한다.

### 재고 확보
- 주문 식별자(참조), 판매 단위 식별자(참조), 수량, 만료 시각, 상태(유지, 확정, 반환)
- 상태 전이: 유지 → 확정 또는 반환. 확정과 반환은 종료 상태다.
- 규칙: 유지 상태의 수량은 이미 재고에서 차감되어 있다. 만료 시각은 결제 방식별 설정값(즉시 결제 15분, 입금 대기 24시간)으로 정하며, 입금 대기 유지 시간은 판매 단위별 상한을 설정으로 둘 수 있다. 반환은 한 번만 일어난다.
- 발송 전 취소로 재고를 더해도 재고 확보 상태는 **확정으로 그대로 둔다**(취소 전용 상태를 만들지 않는다). 재고 가산은 "발송 전 → 취소" 조건부 갱신과 같은 트랜잭션에서 한 번만 한다.
- 결제 대기 주문을 취소하거나 확인 필요로 바꿀 때 유지 상태인 재고 확보는 반환으로 바꾼다. 확인 필요 사유가 재고 확보 만료 뒤 결제 성공이면 재고는 이미 반환되어 있으므로 다시 차감하지 않는다.

### 결제
- 주문 참조, 결제 방식(즉시 결제, 입금 대기), 금액, 상태(준비, 승인 대기, 입금 대기, 성공, 실패, 만료), 대행사 결제 키(선택), 입금 기한(선택, 입금 대기 방식만)
- 상태 전이 (상태머신 그림은 [state-machines.png](diagrams/state-machines.png)에 있다):

| 현재 상태 | 이동 가능한 상태 | 조건 |
|-----------|------------------|------|
| 준비 | 승인 대기 | 즉시 결제, 결제창 진입 |
| 준비 | 입금 대기 | 가상계좌 발급 |
| 준비 | 실패 | 결제 준비 실패 |
| 준비 | 만료 | 결제창에 들어가지 않고 이탈함(유지 시간 경과), 고객이 결제 대기 주문을 취소함 |
| 승인 대기 | 성공 | 승인 확인(서버 조회, 금액 일치) |
| 승인 대기 | 실패 | 결제 실패 |
| 승인 대기 | 만료 | 유지 시간 경과, 고객이 결제 대기 주문을 취소함 |
| 입금 대기 | 성공 | 입금 확인(서버 조회, 금액 일치) |
| 입금 대기 | 만료 | 입금 기한 경과, 고객이 결제 대기 주문을 취소함 |
| 만료 | 성공 | 만료 뒤 승인이나 입금이 서버 조회로 확인됨. 주문은 확인 필요로 간다 |
| 성공, 실패 | (없음) | 종료 |

- 만료는 **만료 → 성공 한 가지 경우를 빼면** 종료 상태다.
- 입금 대기 결제의 만료는 입금 기한 기준이며 입금 기한 만료 처리(UC-18)가 맡는다. 재고 확보 만료 처리(UC-17)는 입금 대기 결제를 만료시키지 않는다.
- 만료 처리 전에는 항상 대행사에 **조회를 먼저** 한다. 조회에서 성공이 확인되면 만료시키지 않고 결제 성공으로 처리한다(주문 상태에 따라 확정 또는 확인 필요).
- 규칙: 청구 금액은 주문 총액과 같아야 한다. 한 주문에 성공 결제는 하나만 있다(부분 유일 인덱스). 주문당 **비종료 결제(준비, 승인 대기, 입금 대기)는 하나만** 있다(부분 유일 인덱스). 환불은 결제 상태를 바꾸지 않고 결제 거래 내역에 환불 행을 추가한다.
- 금액 불일치(대행사가 승인하거나 입금을 확인한 실제 금액이 청구 금액과 다름)는 주문을 확정하지 않고 확인 필요(사유 금액 불일치)로 보낸다. 이때 승인 거래 내역에는 대행사가 알려 준 실제 금액을 기록하고, 환불은 그 실제 금액 전액이다.
- 결제 시작 요청은 **고객이 확인한 금액**을 함께 받는다. 서버가 계산한 주문 총액과 다르면 결제를 시작하지 않고 새 금액으로 다시 확인하게 한다(FR-010). 입금 대기 방식으로 시작하면 [환불 계좌](#환불-계좌)도 함께 받는다.
- 대행사에서 돌아온 화면의 반환 경로(성공, 실패)는 읽기 전용이다. 결과 처리는 멱등키가 있는 POST 승인 확인으로만 하며, 확정과 재고 반환은 서버가 대행사 조회 결과로만 한다.

### 결제 거래 내역 (추가 전용)
- 결제 참조, 유형(승인, 환불), 대상 하위 주문(선택, 환불일 때만), 환불 참조(선택, 환불일 때만), 금액, 대행사 거래 키(선택), 발생 시각
- 규칙: 수정하거나 지우지 않는다. 환불이 완료되면 새 행을 추가한다. 하위 주문별 환불 합계는 그 하위 주문 금액을 넘을 수 없다.

### 환불
- 결제 참조, 대상 하위 주문(선택, 비어 있으면 주문 전체), 금액, 사유(고객 취소, 판매자 취소, 확인 필요 환불, 결제 대기 취소), 상태(요청, 확인 중, 완료, 실패), 멱등키, 시도 번호, 대행사 환불 키(선택), 실패 사유(선택), 요청 시각, 완료 시각(선택)
- 상태 전이: 요청 → 완료, 실패, 확인 중. 확인 중 → 완료, 실패. 완료와 실패는 종료 상태다. "확인 중"은 대행사 호출 결과를 몰라 조회로 확인해야 하는 상태다. 실패한 환불은 재시도 작업이 **새 환불 행(새 멱등키, 시도 번호 + 1)** 으로 이어 간다.
- 환불 행은 취소(상태 변경)와 **같은 트랜잭션에서 "요청"으로 먼저 기록**한 뒤 대행사를 호출한다. 서버가 중간에 죽어도 재시도 작업이 요청 행을 찾아 이어 간다.
- 하위 주문 하나에 **진행 중(요청, 확인 중)이거나 완료된 환불은 하나만** 있다(부분 유일 인덱스). 주문 전체 환불(확인 필요 환불)도 결제 하나에 진행 중이거나 완료된 것은 하나만 있다. 환불 합계(진행 중과 완료)는 하위 주문 금액과 결제로 실제 승인된 금액을 넘을 수 없다(조건부 삽입과 데이터베이스 제약으로 막는다).
- 환불이 완료되면 결제 거래 내역에 환불 행을 더하고 결제 상태는 바꾸지 않는다. 확인 필요 환불이 완료되면 주문을 환불됨으로 바꾼다.
- 환불 호출은 멱등키로 보호한다. 사유 "결제 대기 취소"는 결제 대기 주문을 취소하는 중에 이미 성공한 결제가 확인되어 환불해야 하는 경우에 쓴다.

### 환불 계좌
- 결제 참조, 은행, 계좌번호(암호화 저장), 마스킹 계좌번호, 예금주, 마스킹 시각(선택)
- 규칙: **입금 대기(가상계좌) 방식 결제에만** 있으며 결제당 하나다(유일 제약). 고객이 입금 대기 방식으로 결제를 시작할 때 입력한다. 계좌번호는 암호화해서 저장하고 로그와 감사 이력에 남기지 않는다. 화면에는 마스킹한 값만 보인다. 환불이 완료되면 암호화된 원문을 지우고 마스킹 값만 남긴다. 대행사별 환불 계좌 요구 사양은 구현 전에 확인한다.

### 멱등키
- 범위(결제 시작, 결제 승인, 취소, 환불, 웹훅), 키, 요청 내용 해시, 처리 상태(처리 중, 완료, 실패), 저장된 결과(선택), 점유 만료 시각(선택, 처리 중일 때), 만료 시각
- 상태 전이: 처리 중 → 완료, 처리 중 → 실패. 완료와 실패 키는 만료 시각이 지나면 정리 작업이 지운다.
- 처리 중인 키는 점유 만료 시각이 지나면 다른 요청이 대행사 조회로 상태를 확인해 이어받거나 실패로 바꾼다(점유 회수). 처리 중 오류가 나도 키를 처리 중으로 남기지 않는다.
- 키는 **시도마다 새로 만든다.** 실패한 결과도 저장하며 같은 키로 다시 오면 저장된 실패를 돌려준다. 재시도는 새 키를 쓴다.
- 규칙: (범위, 키)가 유일하다. 같은 키에 내용이 다르면 거절한다.

### 감사 이력
- 대상 종류, 대상 식별자, 이전 상태(선택, 첫 기록은 없음), 이후 상태, 행위자, 발생 시각
- 규칙: 결제, 주문, 하위 주문, 재고 확보, 환불의 상태가 바뀔 때마다 한 행을 추가한다(FR-016). 수정과 삭제는 하지 않는다. 개인정보, 카드 정보, 환불 계좌번호는 담지 않는다.

## 주요 흐름과 데이터 변화

1. **결제 시작**: 고객이 확인한 금액을 서버가 계산한 주문 총액과 대조하고(다르면 시작하지 않고 새 금액으로 다시 확인), 고객당 결제 대기 주문 수와 판매 단위별 수량 상한을 검사한다. 입금 대기 방식이면 환불 계좌를 함께 받아 암호화해 저장한다. 통과하면 한 트랜잭션에서 재고(가용 수량)를 조건부 차감하고, 재고 확보(유지)와 주문(결제 대기), 하위 주문(발송 전), 결제(준비)를 만든다. 하나라도 재고가 부족하면 전체를 되돌린다. 이 단계는 컨텍스트 세 개(재고, 주문, 결제)를 가로지르므로 첫 구현에서는 서비스 인터페이스를 거쳐 한 데이터베이스 트랜잭션으로 묶고, 컨텍스트를 인스턴스로 나눌 때는 보상 처리가 있는 흐름으로 바꾼다([ADR-0007](../../docs/adr/0007-context-deployment-strategy.md)).
2. **결제 성공**: 반환 경로는 읽기 전용이다. 멱등키가 있는 POST 승인 확인(또는 웹훅)을 `PaymentResultCoordinator`가 받아 대행사 조회로 검증한 뒤 결제를 성공으로, 재고 확보를 확정으로, 주문을 확정으로 바꾼다. 확정과 재고 반환은 조회 결과로만 한다.
3. **결제 실패 또는 만료**: 만료 처리 전에 대행사에 조회를 먼저 한다. 성공이 아니면 재고를 더하고 재고 확보를 반환으로, 결제를 실패 또는 만료로, 주문을 취소됨으로, 하위 주문을 취소(주체 시스템)로 바꾼다. 청구된 결제가 없으므로 환불은 없다. 스케줄러는 `PaymentResultCoordinator`를 호출하고 컨텍스트 저장소를 직접 부르지 않는다.
4. **결제 대기 주문 취소(고객)**: 고객이 주문 단위로 취소한다. 대행사 조회로 아직 성공이 아님을 확인한 뒤 한 트랜잭션에서 주문을 취소됨으로, 하위 주문을 취소(주체 고객)로, 재고 확보를 반환으로 바꾸고 재고를 더하며 결제를 만료로 바꾼다. 조회에서 이미 성공이면 취소하지 않고 결제 성공 흐름(2)으로 처리한다. 취소와 결제 성공이 겹치면 먼저 처리된 쪽만 반영한다.
5. **확인 필요와 자동 전액 환불**: 재고 확보 만료 뒤 결제 성공, 만료로 취소된 주문의 만료 뒤 성공(기한 후 입금 포함), 금액 불일치가 서버 조회로 확인되면 결제를 성공(만료 → 성공 포함)으로 기록하고 주문을 확인 필요(사유 기록)로 바꾼다. 같은 트랜잭션에서 아직 취소되지 않은 하위 주문을 취소로, 유지 중인 재고 확보를 반환으로 바꾸고, **주문 전체 환불 행을 "요청"으로 먼저 기록**한 뒤 대행사에 전액 환불을 요청한다. 환불이 완료되면 거래 내역에 환불 행을 더하고 주문을 환불됨으로 바꾸며 환불 계좌 원문을 마스킹으로 바꾼다.
6. **환불 재시도**: 환불 재시도 작업이 `PaymentResultCoordinator`를 통해 요청 상태에서 멈춘 환불과 확인 중인 환불을 대행사 조회로 확인해 이어 간다. 실패한 환불은 새 멱등키의 새 환불 행으로 다시 요청한다. 진행 중이거나 완료된 환불이 이미 있으면 새로 만들 수 없다(부분 유일 인덱스). 계속 실패하는 환불은 운영자가 실패 사유를 조회한다.
7. **발송 전 취소(고객, 판매자)**: 속한 주문이 확정된 하위 주문만 대상이다. 한 트랜잭션에서 하위 주문을 취소(주체, 사유 기록)로 바꾸고, 그 항목의 재고를 더하고, 환불 행(하위 주문 금액 전액)을 "요청"으로 기록한다. 그 뒤 대행사 환불을 멱등키로 요청하고 완료되면 환불 거래 내역을 추가한다. 가상계좌 결제의 환불은 저장된 환불 계좌로 보낸다. 모든 하위 주문이 취소되면 주문을 취소됨으로 바꾼다. 판매자 취소는 사유가 필수다.
8. **문제 신고**: 배송 완료 상태이고 구매 확정 전인 하위 주문에 고객이 사유를 적어 신고하면 문제 신고 시각과 사유를 기록한다. 이 하위 주문은 자동 구매 확정에서 빠지고 운영자가 조회한다.
9. **구매 확정**: 고객이 직접 확정하거나, 배송 완료 시각 기준 7일이 지나고 문제 신고가 없는 하위 주문을 스케줄러가 자동으로 확정한다. 구매 확정 시각을 기록하며 이후 정산 기능이 이 값을 읽는다.
