# 데이터 모델: 멀티 판매자 이커머스 핵심 구매·판매 흐름

모든 금액은 원 단위 정수다. 모든 테이블은 생성 시각과 수정 시각을 가진다. 화면과 외부에 노출되는 식별자는 별도의 공개용 식별자를 쓴다.

## 바운디드 컨텍스트

개체는 일곱 개의 컨텍스트로 나눈다. 컨텍스트는 소스 코드의 기능 단위 패키지와 같다([plan.md](plan.md)의 프로젝트 구조). 그림은 [diagrams/data-model-class.png](diagrams/data-model-class.png)에 있다.

| 컨텍스트 | 맡는 개체 | 맡는 일 |
|----------|-----------|---------|
| 계정 | 계정, 판매자 정보, 입점 서류 | 가입, 로그인, 입점 신청과 승인, 사업자 정보와 서류 보관 |
| 상품 | 상품, 판매 단위 | 상품과 옵션 조합 등록, 검색 |
| 주문 | 장바구니 항목, 주문, 하위 주문, 하위 주문 항목 | 장바구니, 주문 생성, 하위 주문 상태 전이, 취소, 구매 확정 |
| 재고 | 재고, 재고 확보 | 판매 단위별 가용 수량 소유, 재고 선점, 확정, 반환, 만료 처리 |
| 결제 | 결제, 결제 거래 내역 | 결제 승인, 입금 확인, 환불, 대행사 연동 |
| 배송 | 배송 정보 | 송장 입력, 배송 완료 시각 기록 |
| 공통 | 멱등키, 감사 이력 | 여러 컨텍스트가 함께 쓰는 중복 방지와 변경 이력 |

- 컨텍스트 사이의 호출은 서비스 인터페이스로만 하고, 다른 컨텍스트의 저장소는 직접 쓰지 않는다.
- **컨텍스트 사이 참조는 식별자 값으로만 한다.** 다른 컨텍스트 개체를 가리킬 때 데이터베이스 외래키와 조인을 쓰지 않는다. 컨텍스트를 별도 인스턴스로 나눌 수 있게 하려는 규칙이다([ADR-0007](../../docs/adr/0007-context-deployment-strategy.md)). 아래 개체 설명에서 컨텍스트를 넘는 "참조"는 식별자 참조를 뜻한다.
- 판매 단위별 가용 재고 수량은 **재고 컨텍스트의 `재고` 개체가 소유**한다. 상품 컨텍스트의 판매 단위는 재고 수량을 갖지 않는다. 판매자가 상품을 등록하거나 재고를 고치면 상품 컨텍스트가 재고 컨텍스트의 서비스를 호출한다.
- 하위 주문의 배송 상태 전이(취소와 발송이 동시에 올 때 먼저 처리된 요청만 반영하는 규칙 포함)는 주문 컨텍스트가 상태 한 곳에서 조건부로 처리한다. 배송 컨텍스트는 송장과 배송 완료 시각만 맡는다.

## 개체와 관계

```text
고객 1 ─ N 장바구니 항목 N ─ 1 판매 단위 N ─ 1 상품 N ─ 1 판매자
고객 1 ─ N 주문 1 ─ N 하위 주문 N ─ 1 판매자
하위 주문 1 ─ N 하위 주문 항목 N ─ 1 판매 단위
하위 주문 1 ─ 0..1 배송 정보
주문 1 ─ N 결제 1 ─ N 결제 거래 내역
주문 1 ─ N 재고 확보 N ─ 1 판매 단위
판매 단위 1 ─ 1 재고
판매자 1 ─ N 입점 서류
```

## 개체

### 계정 (고객, 판매자, 운영자)
- 유형(고객, 판매자, 운영자), 이메일, 비밀번호 해시, 상태
- 규칙: (유형, 이메일)이 유일하다. 비밀번호는 솔트가 적용된 해시만 저장한다. 고객 계정은 판매 기능을, 판매자 계정은 장바구니와 주문 기능을 쓸 수 없다.

### 판매자 정보
- 계정 참조, 사업자 유형(개인사업자, 법인사업자), 상호명, 사업자등록번호, 대표자명, 연락처, 사업장 주소, 통신판매업 신고번호, 법인명(법인만), 법인등록번호(법인만), 입점 상태(신청, 승인, 거절, 정지)
- 상태 전이: 신청 → 승인 또는 거절, 승인 → 정지, 정지 → 승인. 거절은 종료 상태다.
- 규칙: 사업자등록번호는 유일하다. 법인사업자는 법인명과 법인등록번호가 필수이고 개인사업자는 비어 있어야 한다. 대표자 주민등록번호는 저장하지 않는다. 승인 상태가 아니면 상품을 등록할 수 없고, 정지·거절 판매자의 상품은 고객에게 보이지 않는다. 사업자 등록이 없는 개인은 입점할 수 없다.

### 입점 서류
- 판매자 정보 참조, 서류 종류(사업자등록증 사본 등), 파일 저장 위치, 제출 시각
- 규칙: 판매자 정보를 만들 때 함께 제출된다. 판매자 본인과 운영자만 조회할 수 있다. 파일은 서버가 정한 이름으로 비공개 위치에 저장하고 허용 형식과 크기를 검사한다. 국세청 진위 확인과 정산 계좌는 이번 범위에서 제외한다.

### 상품
- 판매자 참조, 이름, 설명, 사진 목록, 판매 상태(판매 중, 판매 중지)
- 규칙: 하나 이상의 판매 단위를 가진다. 이름은 비어 있을 수 없다.

### 판매 단위 (옵션 조합)
- 상품 참조, 옵션 값 목록(예: 색상=빨강, 사이즈=M), 가격
- 규칙: 가격은 0보다 크다. 한 상품 안에서 옵션 값 조합은 유일하다. 옵션이 없는 상품은 판매 단위가 하나다. 재고 수량은 [재고](#재고) 개체가 소유한다.

### 장바구니 항목
- 고객 참조, 판매 단위 참조, 수량
- 규칙: (고객, 판매 단위)가 유일하다. 수량은 1 이상이다. 재고보다 많은 수량으로는 주문을 시작할 수 없다.

### 주문
- 고객 참조, 총 금액, 상태(결제 대기, 확정, 취소됨, 확인 필요), 배송지 정보
- 상태 전이: 결제 대기 → 확정, 결제 대기 → 취소됨(결제 실패, 시간 초과, 입금 기한 만료), 결제 대기 → 확인 필요(기한 후 입금, 재고 확보 만료 후 결제 성공)
- 규칙: 총 금액은 하위 주문 금액의 합과 같다. 확정 이후에는 하위 주문 상태가 모두 취소이면 주문도 취소됨으로 본다.

### 하위 주문
- 주문 참조, 판매자 참조, 금액, 배송 상태, 구매 확정 시각, 취소 시각 (송장 정보와 배송 완료 시각은 [배송 정보](#배송-정보)가 맡는다)
- 배송 상태 전이 (허용 목록):

| 현재 상태 | 이동 가능한 상태 |
|-----------|------------------|
| 발송 전 | 배송 중, 취소 |
| 배송 중 | 배송 완료 |
| 배송 완료 | 구매 확정 |
| 구매 확정 | (없음) |
| 취소 | (없음) |

- 규칙: 판매자는 자기 하위 주문만 바꿀 수 있다. 발송 전에서만 취소할 수 있다. 배송 완료 후 7일(설정값)이 지나면 자동으로 구매 확정된다. 배송 중과 취소는 서로 배타적이며 상태 변경은 `WHERE 상태 = 현재 상태` 조건부 갱신으로 먼저 처리된 요청만 반영한다.

### 배송 정보
- 하위 주문 참조, 택배사, 송장 번호, 배송 완료 시각
- 규칙: 판매자가 송장을 입력할 때 만들어지고, 하위 주문 하나에 최대 하나다(유일 제약). 송장 입력과 하위 주문의 배송 상태 변경("발송 전" → "배송 중")은 같은 트랜잭션에서 처리하며, 하위 주문이 이미 취소되었으면 송장을 저장하지 않는다. 배송 완료 시각은 판매자가 배송 완료 처리를 할 때 기록한다.

### 하위 주문 항목
- 하위 주문 참조, 판매 단위 참조, 수량, 주문 당시 단가
- 규칙: 주문 당시 단가를 복사해 두어 이후 가격이 바뀌어도 주문 금액이 달라지지 않는다.

### 재고
- 판매 단위 식별자(참조), 가용 수량
- 규칙: 판매 단위마다 하나다(유일 제약). 가용 수량은 0 이상이며 데이터베이스 제약으로 음수를 막는다. 값은 재고 컨텍스트가 조건부 갱신으로만 바꾼다.

### 재고 확보
- 주문 식별자(참조), 판매 단위 식별자(참조), 수량, 만료 시각, 상태(유지, 확정, 반환)
- 상태 전이: 유지 → 확정 또는 반환. 확정과 반환은 종료 상태다.
- 규칙: 유지 상태의 수량은 이미 재고에서 차감되어 있다. 만료 시각은 결제 방식별 설정값(즉시 결제 15분, 입금 대기 24시간)으로 정한다. 반환은 한 번만 일어난다.

### 결제
- 주문 참조, 결제 방식(즉시 결제, 입금 대기), 금액, 상태(준비, 승인 대기, 입금 대기, 성공, 실패, 만료), 대행사 결제 키, 입금 기한
- 규칙: 청구 금액은 주문 총액과 같아야 한다. 한 주문에 성공 결제는 하나만 있다(유일 제약).

### 결제 거래 내역 (추가 전용)
- 결제 참조, 유형(승인, 환불), 대상 하위 주문(환불일 때), 금액, 대행사 거래 키, 발생 시각
- 규칙: 수정하거나 지우지 않는다. 환불은 새 행을 추가한다. 하위 주문별 환불 합계는 그 하위 주문 금액을 넘을 수 없다.

### 멱등키
- 범위(결제 시작, 결제 승인, 취소, 웹훅), 키, 요청 내용 해시, 처리 상태(처리 중, 완료), 저장된 결과, 만료 시각
- 규칙: (범위, 키)가 유일하다. 같은 키에 내용이 다르면 거절한다.

### 감사 이력
- 대상 종류, 대상 식별자, 이전 상태, 이후 상태, 행위자, 발생 시각
- 규칙: 결제, 주문, 하위 주문, 재고 확보의 상태가 바뀔 때마다 한 행을 추가한다(FR-016). 수정과 삭제는 하지 않는다. 개인정보와 카드 정보는 담지 않는다.

## 주요 흐름과 데이터 변화

1. **결제 시작**: 한 트랜잭션에서 재고(가용 수량)를 조건부 차감하고, 재고 확보(유지)와 주문(결제 대기), 하위 주문(발송 전), 결제(준비)를 만든다. 하나라도 재고가 부족하면 전체를 되돌린다. 이 단계는 컨텍스트 세 개(재고, 주문, 결제)를 가로지르므로 첫 구현에서는 서비스 인터페이스를 거쳐 한 데이터베이스 트랜잭션으로 묶고, 컨텍스트를 인스턴스로 나눌 때는 보상 처리가 있는 흐름으로 바꾼다([ADR-0007](../../docs/adr/0007-context-deployment-strategy.md)).
2. **결제 성공**: 대행사 조회로 검증한 뒤 결제를 성공으로, 재고 확보를 확정으로, 주문을 확정으로 바꾼다.
3. **결제 실패 또는 만료**: 재고를 더하고 재고 확보를 반환으로, 주문을 취소됨으로 바꾼다.
4. **발송 전 취소**: 하위 주문을 취소로 바꾸고, 그 항목의 재고를 더하고, 환불 거래 내역을 추가한다. 대행사 환불 요청은 멱등키로 보호한다.
5. **구매 확정**: 하위 주문이 구매 확정이 되면 구매 확정 시각을 기록한다. 이후 정산 기능이 이 값을 읽는다.
