# 작업 목록: 멀티 판매자 이커머스 핵심 구매·판매 흐름

**입력**: `/specs/001-multiseller-commerce-core/`의 설계 문서

**전제 문서**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md), [usecase-details.md](usecase-details.md), [review.md](review.md), ADR-0001~0009(이 브랜치의 `docs/adr/`에 있다. 기준 결정은 ADR-0009)

**관련 이슈**: #3

**테스트**: 헌법 원칙 I(테스트 우선)에 따라 **모든 사용자 스토리에 테스트 작업이 있고, 구현보다 먼저 작성해서 실패를 확인한다.** 테스트 작업을 건너뛰고 구현 작업을 시작해서는 안 된다. 테스트가 컴파일되려면 대상 인터페이스와 빈 구현(스텁)이 먼저 있어야 하므로, **인터페이스 스텁 작업(T166)을 테스트보다 앞에 둔다.** 빨강(실패)에서 초록(통과)까지는 **스토리 브랜치 안에서 끝내고**, 스토리 PR은 모든 테스트가 통과한 상태로만 연다(빨간 테스트만 있는 커밋은 브랜치에는 남아도 되지만 PR 머지 조건은 CI 통과다. 헌법 원칙 I, X).

**조직 방식**: 작업은 사용자 스토리별로 묶어 각 스토리를 독립적으로 구현하고 시험할 수 있게 한다. 각 스토리는 헌법 원칙 X에 따라 이슈를 연결한 브랜치에서 작업하고 PR로 완료를 요청한다.

**서비스 먼저, 화면은 나중에**: 화면 디자인은 외부에서 따로 진행 중이다. 그래서 1~8단계는 서비스(백엔드)를 REST API만으로 끝까지 만들고 시험하며, **디자인이 끝나는 시점에 9단계에서 프론트엔드를 별도 인스턴스로 만든다**(ADR-0007의 방향과 같다).
- 화면과 API 클라이언트 작업 18건(T028, T029, T031, T051, T052, T053, T054, T065, T066, T067, T105, T106, T107, T123, T124, T125, T138, T139)은 번호를 그대로 두고 9단계로 옮겼다. 원래 자리에는 이동 표시만 남겼다. 설계 검토 결정(ADR-0009)으로 생긴 화면은 T221에 모았다.
- 1~8단계의 종단 간 시험(T039, T060, T085, T116, T140)과 "화면에 보인다"는 표현은 **화면 없이 REST API 응답으로** 확인한다.
- 사람 시간 기준 성공 기준(SC-001, SC-002, SC-007, SC-008)의 수동 확인은 프론트엔드가 생긴 뒤 9단계에서 한다(T163).
- 백엔드가 프론트엔드에 넘길 것(로그인 API, OpenAPI 명세, 개발용 시드 데이터)은 T154~T158에서 만든다.

**설계 검토 반영(2026-10-12)**: [review.md](review.md)의 결정은 [ADR-0009](../../docs/adr/0009-review-decisions-payment-refund-scope.md)에 모았고 승인됐다. 그래서 결정이 끝난 작업(T009, T127, T148, T149)은 닫았고, 거기서 생긴 구현은 T166 이후의 새 작업 번호로 이었다. 기존 작업 번호는 바꾸지 않았다. 새 작업은 T166부터 이어 붙였으며, 각 새 기능마다 테스트 작업이 구현 작업보다 앞에 오도록 스토리 절의 테스트 소절과 구현 소절에 나눠 넣었다.

## 형식: `- [ ] T### [P] [US#] 설명과 파일 경로`

- **[P]**: 병렬로 할 수 있다(서로 다른 파일이고 끝나지 않은 작업에 의존하지 않는다).
- **[US#]**: 사용자 스토리 번호(US1~US5). 설정, 기반, 마무리 단계에는 붙이지 않는다.
  - **US1**: 판매자 입점과 상품 등록(P1)
  - **US2**: 고객 가입과 상품 탐색(P1)
  - **US3**: 장바구니, 결제, 주문(P1)
  - **US4**: 판매자 배송 처리와 구매 확정(P2)
  - **US5**: 고객 발송 전 취소(P2). 판매자 직접 취소도 여기서 한다.
- 설명에는 정확한 파일 경로를 적는다. 데이터 모델의 제약은 원문 그대로 인용한다. 설계 검토로 새로 생긴 제약은 ADR-0009의 표현을 쓴다.

## 공통 규칙 (모든 작업에 적용)

- **시각은 주입한다**: 업무 규칙과 SQL에서 `now()`나 `current_timestamp`를 쓰지 않고 `TimeProvider`의 시각을 질의 파라미터로 넘긴다(만료 조회, 자동 확정, 점유 만료 등). 그래야 시험에서 시간을 고정할 수 있다(T021, T169).
- **동시성 시험**: 연결 풀 크기는 동시 스레드 수 이상으로 설정하고, 출발 래치로 한꺼번에 시작하며, 대기에는 제한 시간을 둔다(T170). "같은 요청을 10번"이라는 시험은 **동시 10건과 순차 10건 둘 다** 한다.
- **정의되지 않은 값은 설정값으로 둔다**: 페이지 크기와 정렬, 파일 크기와 형식, 대행사 제한 시간과 재시도·재조회 주기, 멱등키 만료 시간과 점유 시간, 입금 기한 같은 값은 코드에 박지 않고 `application.yml` 설정으로 두며, 기본값은 문서(`docs/configuration.md`)에 적는다(T168).
- **외부 식별자**: 외부에 내보내는 개체는 내부 식별자 대신 `public_id`를 쓴다(T173, T174).

## 경로 규칙

소스 루트는 `src/main/java/kr/shopflow/`(아래 `…/`로 줄여 쓴다), 테스트 루트는 `src/test/java/kr/shopflow/`(아래 `테스트/`)다. 컨텍스트 패키지(`account`, `product`, `order`, `inventory`, `payment`, `delivery`, `common`) 안은 `api`(스프링 데이터 REST 리소스와 동작 컨트롤러), `service`(업무 규칙), `repository`(스프링 데이터 JPA)로 나눈다. 이 저장소의 백엔드에는 화면(`web`)과 API 클라이언트(`client`) 패키지를 두지 않는다. 둘은 9단계의 별도 프론트엔드 인스턴스에서 만든다(plan.md의 계층 구조 1번이 프론트엔드로 옮겨 가는 시점이 앞당겨진 것이다). 클래스와 파일 이름은 영문 코드 식별자를 쓴다.

## 3단계: 사용자 스토리 1 - 판매자가 입점하고 상품을 등록한다 (우선순위: P1) 🎯 MVP

**목표**: 판매자가 사업자 정보와 증빙 서류로 입점을 신청하고, 운영자가 승인하면 옵션과 재고가 있는 상품을 등록하고 수정하고 판매를 중지할 수 있다. 거절되면 사유를 확인하고 서류를 고쳐 다시 신청할 수 있다.

## 5단계: 사용자 스토리 3 - 고객이 장바구니에 담고 결제해 주문한다 (우선순위: P1)

**목표**: 고객이 여러 판매자의 상품을 한 장바구니에 담아 한 번에 주문한다. 결제를 시작하면 재고가 먼저 확보되고, 결제 성공 시 주문이 확정되며, 실패나 시간 초과 시 재고와 주문이 되돌아간다. 같은 결제 요청이 여러 번 와도 결제는 한 번만 일어난다. 즉시 결제와 입금 대기(가상계좌)를 모두 지원한다. 결제 시작 때 고객이 확인한 금액을 대조하고, 결제 대기 주문은 고객이 취소할 수 있으며, 만료 뒤 성공과 기한 후 입금은 자동으로 전액 환불된다.

## 의존 관계와 실행 순서

### 단계 의존 관계

- **설정(1단계)**: 의존 없음. 바로 시작한다. ADR 확정(T009)은 끝났으므로(ADR-0009와 수정된 ADR-0001·0002·0003·0008이 "승인됨", 이 브랜치의 `docs/adr/`) 후속 작업을 막지 않는다. 결정 항목(T127, T148, T149)도 모두 결정되어 구현 전에 정해야 할 것이 남아 있지 않다. T010은 저장소 설정이라 별도로 한다.
- **기반(2단계)**: 설정이 끝나야 한다. 인터페이스 스텁(T166)을 가장 먼저 만든다. **모든 사용자 스토리를 막는다.**
- **사용자 스토리(3~7단계)**: 모두 기반이 끝나야 한다.
  - **US1을 먼저 끝낸다.** US2는 US1 뒤에 시작한다(US1의 `Account`, 마이그레이션, 상품·재고 엔티티, 고객용 목록 기본형을 쓰고 `ProductRepository`와 `ProductQueryService`를 같은 파일에서 고치기 때문이다. review.md W-01).
  - US3은 상품(US1)과 고객 계정(US2)을 쓰므로 US1, US2 뒤에 한다.
  - US4는 확정된 주문이 필요하므로 US3 뒤에 한다.
  - US5는 US3(결제와 환불, 환불 개체 T201~T204)과 US4(하위 주문 상태 전이, 정지 판매자 규칙 T215) 뒤에 한다.
- **마무리(8단계)**: 원하는 스토리가 모두 끝난 뒤. 마지막 인계 점검(T158)이 끝나면 백엔드는 프론트엔드가 필요로 하는 것을 모두 낸 상태다.
- **프론트엔드(9단계)**: 외부 디자인 완료(T161), 인계 점검(T158), 방식 결정(T159)이 모두 끝나야 시작한다. 백엔드 1~8단계와 시간이 겹치지 않아도 되고, 디자인이 끝나는 시점에 맞춰 시작한다. 백엔드의 US별 API가 확정되는 대로 해당 화면부터 먼저 만들 수도 있다.

### 스토리 안의 순서

- 인터페이스 스텁(T166) → 테스트를 먼저 쓰고 **실패를 확인한 뒤** 구현한다(헌법 원칙 I). 빨강에서 초록까지는 스토리 PR 안에서 끝낸다.
- 마이그레이션 → 엔티티 → 리포지토리 → 서비스 → REST API 순서다(API 클라이언트와 화면은 9단계에서 한다).
- US3 안에서는 `PaymentResultCoordinator`(T200)와 환불(T201~T203)을 스케줄러(T101, T204)와 웹훅(T103), 승인 확인(T207)보다 먼저 만든다.
- 스토리를 끝낼 때마다 통합 점검 작업과 PR(`Closes #번호`)로 마무리한다.

### 병렬 기회

- 설정의 [P] 작업(T002~T008)은 서로 병렬이다.
- 기반의 테스트 작업(T011~T018, T167, T169, T171, T173)은 스텁(T166) 뒤에 모두 병렬이고, 구현 작업의 [P](T020~T025, T027, T168, T170)도 병렬이다.
- 각 스토리의 테스트 작업은 대부분 [P]이다. 서로 다른 테스트 파일이기 때문이다.
- 같은 스토리 안에서 서로 다른 컨텍스트의 엔티티(예: T090, T091, T092, T202)는 병렬이다.
- US1과 US2는 직렬이다. 병렬로 하지 않는다.
- 9단계의 화면과 API 클라이언트 작업([P])은 백엔드와 별개로 병렬로 할 수 있다. 시작 조건은 9단계 첫머리에 있다.

## 구현 전략

### 첫 시연 가능한 범위 (MVP)

1. 1단계 설정, 2단계 기반을 끝낸다.
2. **사용자 스토리 1**(판매자 입점과 상품 등록)을 끝낸다. 판매자가 상품을 올리고 고객용 상품 목록 API에 보이면 첫 가치가 전달된다. 화면이 없으므로 시연은 API 호출(OpenAPI 문서 화면이나 시험 결과)로 한다.
3. 거기서 멈추고 시연한다.

### 판매가 가능한 최소 범위

실제로 사고팔 수 있으려면 **사용자 스토리 1~3(P1)** 이 모두 필요하다. 이 범위가 끝나면 결제와 재고의 핵심 규칙(재고 선점, 멱등 결제, 시간 초과 반환, 만료 뒤 성공 자동 환불)이 끝까지 검증된다.

### 단계별 전달

1. 설정 + 기반 → 기반 완성
2. US1 → 시험 → PR (MVP)
3. US2 → 시험 → PR (US1 뒤에 직렬로)
4. US3 → 시험 → PR (판매 가능)
5. US4 → 시험 → PR
6. US5 → 시험 → PR
7. 마무리 + 프론트엔드 인계 준비(T156~T158) → 기능 PR (백엔드 완료)
8. 디자인 완료 시점에 9단계 프론트엔드 → 별도 이슈와 브랜치, PR(헌법 원칙 X)

### 위험과 주의

- **스프링 데이터 REST 노출 범위**: 쓰기 요청이 거절되는지, 남의 것이 보이지 않는지 테스트(T012, T142)로 항상 지킨다.
- **컨텍스트를 가로지르는 흐름**(결제 시작, 결제 성공, 발송 전 취소, 환불): 첫 구현은 한 트랜잭션이지만 단계마다 멱등하게 만들어 나중에 보상 처리로 바꿀 수 있게 한다(ADR-0007). 비동기 결제 결과는 `PaymentResultCoordinator`만 지휘한다.
- **돈이 걸린 경계**: 환불은 한 번만 일어나야 한다. 환불 행은 취소와 같은 트랜잭션에서 먼저 기록하고, 유일 제약과 합계 상한은 DB가 막는다(T196, T201). 환불 계좌 번호는 암호화하고 로그에 남기지 않는다(T197).
- **미정 항목**: 설정값의 기본값(T168)과 가상계좌 환불의 대행사별 사양(T098)은 구현 전에 문서와 대행사 문서로 확인한다. 값을 이 문서에서 지어내지 않는다.
- 작업이 끝날 때마다 커밋하고, 스토리 단위로 PR을 연다(헌법 원칙 X).
