# 조사 결과: 멀티 판매자 이커머스 핵심 구매·판매 흐름

헌법이 정하지 않은 항목(빌드 도구, 데이터베이스, 결제 대행사)과 명세가 계획 단계로 미룬 항목을 정리한다. 모든 결정은 이 문서에 근거를 남긴다.

## 1. 빌드 도구

- **결정**: 그레이들
- **근거**: 스프링 부트의 기본 안내가 그레이들 기준이고, 테스트 병렬 실행과 의존성 관리가 편하다.
- **검토한 대안**: 메이븐. 설정이 단순하지만 팀이 이미 정한 선호가 없고 기능 차이가 크지 않다.

## 2. 데이터베이스와 마이그레이션

- **결정**: 포스트그레스큐엘과 플라이웨이
- **근거**: 조건부 갱신, `SELECT ... FOR UPDATE SKIP LOCKED`, 유일 제약 등 재고와 멱등키 처리에 필요한 기능이 안정적이다. 테스트도 같은 데이터베이스를 테스트컨테이너스로 띄워 운영과 동작 차이를 없앤다.
- **검토한 대안**: 메모리 데이터베이스(H2). 빠르지만 잠금과 동시성 동작이 달라 재고 검증을 믿기 어렵다. 마이에스큐엘. 가능하지만 이 프로젝트에는 포스트그레스큐엘의 기능이 더 맞는다.

## 3. 결제 대행사

- **결정**: 토스페이먼츠
- **근거**: 카드 즉시 결제와 가상계좌를 한 대행사에서 지원하고, 결제 승인 조회 API와 웹훅, 멱등키 헤더를 제공한다. 개발용 테스트 키로 실제 결제 없이 검증할 수 있다.
- **검토한 대안**: 포트원(여러 대행사 중개)은 대행사 교체가 쉽지만 한 단계가 더 늘어 첫 기능에는 과하다. 직접 계약은 심사 기간 때문에 제외한다.
- **완화책**: 결제를 `PaymentGateway` 포트로 감싸 대행사를 바꿔도 도메인 코드가 바뀌지 않게 한다. 테스트에서는 가짜 구현을 쓴다.
- **확인 필요**: 실제 가맹 계약과 운영 키 발급은 구현 범위 밖이며, 개발 단계에서는 테스트 키만 쓴다.

## 4. 재고 선점과 동시성

- **결정**: 판매 단위 행에 대한 조건부 갱신으로 재고를 차감하고, 같은 트랜잭션에서 재고 확보 행을 만든다.
  - 차감: `UPDATE ... SET stock = stock - :수량 WHERE id = :id AND stock >= :수량`. 갱신 행이 0이면 재고 부족이다.
  - 확정: 결제 성공 시 재고 확보 상태를 확정으로 바꾼다(재고는 이미 차감됨).
  - 반환: 실패, 만료, 취소 시 재고를 더하고 상태를 반환으로 바꾼다. 상태는 한 번만 바뀌도록 `WHERE 상태 = 유지` 조건을 둔다.
- **근거**: 비관적 잠금보다 단순하고 교착 가능성이 낮다. 유일한 진실은 데이터베이스 한 곳이다.
- **검토한 대안**: 낙관적 잠금(버전 컬럼)은 충돌 시 재시도가 필요해 코드가 복잡하다. 레디스 선점은 새 의존성을 추가해 단순성 원칙에 어긋난다.

## 5. 만료 처리

- **결정**: 스프링 스케줄러가 1분마다 만료된 재고 확보를 `FOR UPDATE SKIP LOCKED`로 가져와 반환한다. 구매 확정 자동 처리와 입금 기한 만료도 같은 방식으로 한다.
- **근거**: 서버가 여러 대로 늘어도 같은 행을 두 번 처리하지 않는다. 별도 작업 큐가 필요 없다.
- **검토한 대안**: 지연 큐나 분산 스케줄러. 현재 규모에는 과하다.

## 6. 멱등키

- **결정**: `idempotency_key` 테이블에 (범위, 키)를 유일 제약으로 두고, 요청 내용 해시와 처리 결과를 저장한다.
  - 같은 키와 같은 내용이 다시 오면 저장된 결과를 돌려준다.
  - 같은 키인데 내용이 다르면 오류로 거절한다.
  - 처리 중에 같은 키가 들어오면 유일 제약으로 하나만 진행하고 나머지는 처리 중임을 알린다.
- **적용 대상**: 결제 시작, 결제 승인, 취소·환불, 대행사 웹훅(대행사가 주는 이벤트 식별자를 키로 사용)
- **근거**: 헌법 VIII을 구조적으로 만족하고 동시 요청에도 안전하다.

## 7. 결제 검증 방식

- **결정**: 고객은 대행사 결제창에서 결제한다. 돌아온 결과를 믿지 않고, 서버가 대행사에 승인 결과를 직접 조회해 금액과 주문 번호를 주문 총액과 대조한 뒤 확정한다.
- **근거**: 헌법 II의 서버 검증 원칙. 카드번호가 서버를 지나가지 않는다.
- **입금 대기**: 가상계좌 발급 후 입금 완료는 웹훅으로 받는다. 웹훅도 같은 대행사 조회로 다시 확인한 뒤 확정한다.

## 8. 사진 저장

- **결정**: 저장소 인터페이스 뒤에 두고 첫 구현은 서버 디스크를 쓴다. 파일 형식과 크기를 검사하고, 파일 이름은 서버가 정한다.
- **근거**: 첫 기능 범위를 줄인다. 외부 저장소로 바꿔도 호출 코드는 그대로다.
- **검토한 대안**: 처음부터 클라우드 객체 저장소를 쓰는 방법. 운영 설정이 늘어나 이번 범위에 과하다.

## 9. 금액 표현

- **결정**: 원 단위 정수(`long`)를 담는 `Money` 값 객체. 부동소수점을 쓰지 않는다. 이번 범위에는 비율 계산(수수료)이 없어 반올림 규칙은 정산 기능에서 정한다.

## 10. 인증 구조

- **결정**: 고객, 판매자, 운영자를 분리한 세 가지 계정 유형을 하나의 인증 체계에서 역할로 구분한다. 고객 계정과 판매자 계정은 서로 다른 계정이며, 같은 이메일로 각각 만들 수 있는지는 "유형별로 이메일이 유일하다"로 정한다(명세 FR-002).
- **근거**: 명세의 계정 분리 결정을 따르면서 구현을 단순하게 유지한다.

## 11. 주문 번호와 외부 노출 식별자

- **결정**: 주문과 하위 주문에는 추측하기 어려운 공개용 식별자를 따로 둔다. 순번 식별자는 내부에서만 쓴다.
- **근거**: 다른 사람의 주문 번호를 추측해 조회하는 공격을 막는다.

## 12. 이번 계획에서 미룬 것

- 성능 부하 시험 도구 선정은 구현 후반에 정한다.
- 이메일 알림, 택배사 연동, 정산은 범위 밖이다.
