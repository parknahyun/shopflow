# day3-example 헌법

## 핵심 원칙

### I. 테스트 우선 품질 (타협 불가)
테스트 주도 개발(TDD)을 필수로 한다. 동작을 바꾸는 모든 변경은 테스트를 먼저 작성하고, 테스트가
실패하는 것을 확인한 뒤에야 구현한다. 빨강-초록-리팩터링 순서를 반드시 지켜야 하며, 해당 변경을
검증하는 테스트가 없는 구현 코드는 머지해서는 안 된다.

- 비즈니스 로직은 반드시 단위 테스트를 갖춘다. 컨트롤러, 영속성, 보안 규칙은 반드시 스프링
  통합 테스트(`@WebMvcTest`, `@DataJpaTest`, `@SpringBootTest` 등)로 검증한다.
- 결제, 주문, 재고 흐름은 성공 경로와 실패 경로를 모두 다루는 종단 간 테스트를 반드시 갖춘다.
- 머지 전에 지속적 통합(CI)에서 전체 테스트가 반드시 통과해야 한다. 실패하거나 건너뛴 테스트는
  사유를 문서로 남기지 않는 한 머지해서는 안 된다.

이유: 테스트를 먼저 실패시켜 보면 테스트가 결함을 실제로 잡아내는지 확인할 수 있고, 명세가 실행
가능한 상태로 유지된다.

### II. 결제·보안 신뢰성
개인정보와 결제정보는 반드시 최소 권한 원칙으로 다룬다.

- 카드번호 원문은 저장하거나 로그에 남겨서는 안 된다. 결제 처리는 인증된 결제 대행사에 맡기고,
  결제 결과는 클라이언트 값을 믿지 말고 반드시 서버에서 검증한다.
- 결제 요청과 결제사 콜백은 반드시 멱등하게 처리하고, 청구 금액은 서버에 저장된 주문 총액과
  반드시 대조한다.
- 비밀번호는 솔트가 적용된 해시로만 저장한다(스프링 시큐리티의 `PasswordEncoder`). 비밀키와
  토큰은 저장소에 커밋해서는 안 되며, 개인정보는 로그에 남겨서는 안 된다.
- 상태를 바꾸는 모든 요청에는 사이트 간 요청 위조 방어와 권한 검사를 적용한다. 모든 사용자 입력은
  서버에서 검증하고, 템플릿에서는 출력 시 이스케이프 처리한다.
- 알려진 치명적 취약점이 있는 의존성은 사용해서는 안 된다.

이유: 쇼핑몰은 고객의 신원과 돈을 다룬다. 유출이나 이중 결제는 피해가 크고 되돌리기 어렵다.

### III. 주문·재고 무결성
주문, 결제, 재고의 상태 변경은 일관되고 추적 가능해야 한다. 재고 차감과 주문 생성은 반드시
원자적으로 처리하고, 결제 콜백과 주문 제출은 반드시 멱등하게 처리한다. 주문 상태 전이는 반드시
허용된 전이 목록에 따라 검증한다.

이유: 초과 판매, 이중 결제, 주문 유실은 고객과 매출에 바로 피해를 준다.

### IV. 단순성 우선
기능은 명세를 충족하는 가장 단순한 설계로 시작한다. 복잡성(서비스 추가, 추상화, 의존성)을 더하려면
반드시 계획서에 근거를 적는다.

이유: 작고 이해하기 쉬운 코드가 테스트하고 보호하기 쉽다.

### V. 한글 산출물과 직관적 표현
모든 산출물은 반드시 한글로 작성한다. 명세, 계획, 작업 목록, 문서, 커밋 메시지, 리뷰 코멘트,
사용자에게 보이는 화면 문구가 모두 해당한다. 문장은 복잡한 표현이나 불필요한 전문 용어 없이
처음 읽는 사람도 바로 이해할 수 있게 짧고 직관적으로 쓴다.

- 처음 쓰는 전문 용어는 반드시 짧은 설명을 함께 적는다.
- 한 문장에는 하나의 내용만 담는다.

이유: 팀 모두가 같은 내용을 같은 뜻으로 이해해야 검토와 합의가 빨라지고 오해로 인한 결함이
줄어든다.

### VI. 영문 표기의 한글 전환
산출물 안의 모든 영문은 반드시 한글로 바꿔 쓴다. 섹션 제목, 기술 명칭, 약어, 라벨이 모두 해당한다.
기술 명칭은 한글 표기를 쓴다(예: 스프링 부트, 타임리프, 스프링 시큐리티).

- 예외는 원문을 바꾸면 동작하지 않는 것으로 한정한다. 코드 식별자, 명령어, 파일 경로, 설정 키,
  외부 도구의 출력이 해당하며, 반드시 백틱(`)으로 표시한다.
- 예외에 해당하지 않는 영문이 산출물에 남아 있으면 리뷰에서 반드시 한글로 고치게 한다.

이유: 표기를 한 가지로 통일해야 읽는 사람이 영문과 한글을 오가며 해석하는 부담이 사라진다.

### VII. 판매자별 분리 관리
이 쇼핑몰은 여러 판매자가 입점하는 구조로 본다. 하나의 주문에 여러 판매자의 상품이 섞여 있으면
반드시 판매자별 하위 주문으로 나눈다. 배송, 정산, 환불은 반드시 이 하위 주문 단위로 따로 관리한다.

- 한 판매자의 배송 지연이나 환불이 다른 판매자의 하위 주문 상태에 영향을 주어서는 안 된다.
- 판매자는 자기 하위 주문, 배송, 정산 내역만 볼 수 있어야 한다. 이 접근 제한은 반드시 서버의
  권한 검사로 강제하고, 테스트로 검증한다.
- 고객에게는 전체 주문을 한 번에 보여 주되, 상태는 하위 주문별로 표시한다.

이유: 배송과 정산의 책임이 판매자마다 다르므로, 관리 단위를 처음부터 나눠야 나중에 고치는 비용이
들지 않는다.

### VIII. 재고 선점과 멱등 결제
결제를 시작하기 전에 반드시 재고를 선점한다. 선점한 재고는 결제가 성공하면 확정하고, 실패하거나
제한 시간이 지나면 반드시 자동으로 되돌린다.

- 결제 요청에는 반드시 멱등키를 붙인다. 같은 멱등키의 요청이 네트워크 재시도, 중복 클릭, 결제사
  콜백 재전송으로 여러 번 들어와도 결제는 반드시 한 번만 일어나고, 모든 요청이 같은 결과를 받는다.
- 멱등키와 처리 결과는 반드시 저장소에 기록하고, 동시에 들어온 같은 키의 요청은 한 건만
  처리되도록 막는다.
- 재고 선점 만료 시간은 반드시 설정값으로 둔다. 선점 중인 재고는 다른 고객이 구매할 수 없다.
- 동시 요청, 재시도 중복, 선점 만료는 반드시 자동화된 테스트로 검증한다.

이유: 재고가 부족한데 결제만 되거나, 같은 결제가 두 번 나가는 사고를 구조적으로 막기 위해서다.

### IX. 정산·환불 규칙의 확장성과 추적성
정산과 환불은 앞으로 요구사항이 계속 늘어날 것으로 본다. 그래서 처음부터 규칙을 바꾸기 쉽고
과거 내역을 추적할 수 있게 만든다.

- 정산은 반드시 하위 주문의 배송이 완료된 뒤에 확정한다. 확정 시 판매 금액에서 수수료를 공제하고,
  환불된 금액은 반드시 차감한다.
- 수수료율과 환불 정책은 코드에 직접 쓰지 말고 설정 또는 데이터로 관리한다. 적용 시점과 변경 이력을
  반드시 남기고, 정산 시점에 적용된 값을 기록해 둔다. 이미 확정된 정산은 정책이 바뀌어도 달라지지
  않아야 한다.
- 돈의 입출금과 조정(수수료 공제, 환불, 정정)은 수정하거나 지우지 않고 항목을 추가하는 방식의
  원장으로 기록한다. 정정이 필요하면 반대 항목을 새로 추가한다.
- 금액 계산은 부동소수점을 쓰지 않고 원 단위 정수 또는 정확한 십진수로 한다. 반올림 규칙은
  반드시 명시하고 테스트로 고정한다.
- 부분 환불, 여러 번 나눈 환불, 정산 확정 이후의 환불(다음 정산에서 차감)은 반드시 지원하며,
  각각 테스트로 검증한다.

이유: 수수료, 환불, 정산 주기는 사업 방식에 따라 자주 바뀐다. 규칙을 분리하고 이력을 남겨야
변경에 안전하게 대응하고 금액 분쟁을 설명할 수 있다.

## 제품 배경

이 프로젝트는 이커머스 쇼핑몰이다. 세부 범위(상품, 장바구니, 결제, 계정, 관리자)는 이 헌법이
아니라 기능별로 `/speckit-specify`에서 정의한다.

## 기술 스택

- 애플리케이션은 반드시 스프링 부트(자바)로 만든 서버 렌더링 웹 애플리케이션이어야 한다.
- 화면은 반드시 서버 사이드 템플릿 엔진을 사용하며, 기본값은 스프링 MVC와 연동한 타임리프이다.
  별도의 단일 페이지 앱(SPA) 프론트엔드 프레임워크를 도입하려면 근거를 문서로 남겨야 한다.
- 인증과 인가는 반드시 스프링 시큐리티를 사용한다.
- 데이터 접근은 반드시 스프링 데이터를 거치고, 스키마 변경은 버전 관리되는 마이그레이션으로 한다.
- 여기서 정하지 않은 항목(빌드 도구, 데이터베이스, 결제 대행사)은 반드시 계획서에서 결정하고
  기록한다.

이유: 하나로 통합된 잘 지원되는 스택은 코드를 단순하게 유지하고, 보안과 테스트 기능을 기본으로
제공한다.

## 개발 워크플로

- 작업은 반드시 스펙 킷 순서(명세, 계획, 작업 분해, 구현)를 따른다.
- 작업 목록은 구현 작업보다 그것을 검증하는 테스트 작업을 먼저 배치한다.
- 변경은 한 번에 검토할 수 있는 크기로 작게 유지한다. 큰 작업은 독립적으로 테스트 가능한 작업으로
  나눈다.

## 품질 게이트

- 모든 테스트가 통과해야 변경이 완료된 것으로 본다.
- 모든 리뷰에서 이 헌법 준수 여부를 확인한다. 구현보다 테스트가 먼저 작성되었는지도 포함한다.
- 결제, 인증, 개인정보를 다루는 변경은 리뷰에서 반드시 보안 점검을 명시적으로 거친다.
- 산출물이 한글이고 이해하기 쉬운지, 예외가 아닌 영문이 남아 있지 않은지 리뷰에서 확인한다.
- 원칙에서 벗어나는 경우에는 계획서나 풀 리퀘스트에 사유를 반드시 기록한다.

## 거버넌스

이 헌법은 다른 모든 프로젝트 관행보다 우선한다. 개정은 이 파일에 기록하고, 변경 이유를 밝히며,
아래 버전을 올려야 한다. 버전은 의미 기반 규칙을 따른다. 하위 호환이 깨지는 원칙 삭제나 재정의는
메이저, 원칙 추가나 지침의 실질적 확장은 마이너, 표현 정리와 오탈자 수정은 패치로 올린다. 모든
계획 리뷰와 코드 리뷰에서 준수 여부를 확인하며, 정당한 사유 없는 위반은 승인할 수 없다.
